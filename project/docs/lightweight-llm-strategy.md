# 초경량 LLM(4B) 기반 검증 엔지니어 시스템 설계 결론

## 1. 배경 및 문제 정의

- **모델 환경**: 로컬 노트북, 4B 경량 LLM 단일 인스턴스
- **태스크**: 이미지 코드 품질 QA (SNR, dark current 등 이미지 센서 특성 평가)
- **사용 패턴**: "X를 평가하고 분석해줘" 형태의 단계 전개형 요청
- **제약**:
  - RAG 사용 불가 (도메인 지식은 skill로 보강)
  - 실시간 응답성은 단계별 전개라 다소 양보 가능
  - 외부 고성능 LLM 사용 가능 여부에 따라 Case 분리

## 2. 핵심 설계 철학

> **"평가는 코드가, 해석은 LLM이."**
> 4B 모델이 약한 영역(수치 계산, 자유 분해, 긴 컨텍스트 종합 추론)은 코드와 사전 정의로 회피하고,
> LLM은 잘 하는 영역(분류, 짧은 자연어 생성, 구조화된 입력 해석)만 담당한다.

### 합의된 원칙

| 원칙 | 내용 |
|---|---|
| 분해는 사전에 | LLM이 런타임 자유 분해 ❌ → Skill 작성 시점에 사람이 분해 |
| 측정은 결정론적 | 수치 산출은 코드, LLM은 추측 ❌ |
| 단계 간 통신은 JSON | 자연어 흐림 차단, 노이즈 누적 방지 |
| UNSURE 명시 허용 | 4B 환각 방지 (강제 답변 금지) |
| 깊이는 최대 2단 | 누적 오차 폭발 방지 |
| 통합 시스템 만들지 않음 | Case 1과 Case 2는 독립 구현 |

## 3. 두 Case 독립 구현

### 3.1 Case 1: 로컬 4B 전용 (인터넷 불가)

**철학**: LLM 호출 최소화, 코드로 결정론화

#### 아키텍처

```
[사용자 요청]
        ↓
┌───────────────────────────────────────────┐
│ Stage 1: Skill Router                     │
│   Local 4B, 1회 호출                      │
│   - 카탈로그에서 skill 1개 선택           │
│   - 출력: JSON {skill, params, confidence}│
│   - confidence=unsure → 사용자 확인       │
└───────────────────────────────────────────┘
        ↓
┌───────────────────────────────────────────┐
│ Stage 2: Skill Execution                  │
│   순수 Python, LLM 호출 0회               │
│   - 굵은 입도 skill (end-to-end 절차)     │
│   - 측정 + 정상범위 비교 + 판정 모두 포함 │
│   - 출력: 표준 dict (metrics, verdicts,   │
│           summary_lines, domain_context)  │
└───────────────────────────────────────────┘
        ↓
┌───────────────────────────────────────────┐
│ Stage 3: Analysis Generation              │
│   Local 4B, self-consistency N=3          │
│   - 입력: summary + verdict + 도메인 룰   │
│   - few-shot 예시 2~3개 필수              │
│   - 출력: JSON {verdict, findings, recos} │
│   - 3회 샘플링 후 필드별 다수결           │
│   - 템플릿으로 자연어 리포트 조립         │
└───────────────────────────────────────────┘
        ↓
[최종 답변]
```

#### Skill 작성 원칙

- **굵은 입도**: 사용자 요청 하나를 거의 완결시키는 단위
- **End-to-end 절차**: 측정 → 비교 → 판정까지 한 묶음
- **분기 로직도 코드 내부**에 포함
- **출력은 항상 동일 스키마**

#### 단계별 사양

| 단계 | LLM 호출 | 입력 토큰 | 출력 토큰 | 목적 |
|---|---|---|---|---|
| Stage 1 | 1회 | ~500 | ~50 | 분류 (생성 X) |
| Stage 2 | 0회 | — | — | 결정론적 측정 |
| Stage 3 | 3회 (SC) | ~1500 | ~200 | 자연어 분석 |

#### 명시적으로 수용한 한계

- 카탈로그에 없는 요청은 "지원하지 않음" 응답
- 자유 복합 요청 처리 불가 (별도 비교 skill로 대응)
- Skill 추가에 개발 비용 발생 (도메인이 좁아 감내 가능)

---

### 3.2 Case 2: 외부 고성능 LLM 가능 (Case 1 기반 확장)

**철학**: Case 1 자산 재활용 + 외부 LLM에 단계적 자유도 부여

#### 핵심 컨셉: 3가지 운용 모드

```
권한 약함 ◄─────────────────────────────────────► 권한 강함

[Mode A: AS-IS]      [Mode B: PARAMETRIZE]    [Mode C: MODIFY]
skill 그대로 호출    파라미터만 조정           skill 코드 수정 후 실행
   ↑                       ↑                       ↑
  Case 1과 동일      대부분의 응용 케이스       자유 변형 요청
```

LLM이 요청을 받으면 **어느 모드로 처리할지부터 결정**.

#### 아키텍처

```
[사용자 요청]
        ↓
┌──────────────────────────────────────────────┐
│ Stage 1: Mode Decision + Plan                │
│   외부 LLM, tool-calling                     │
│                                              │
│   입력: 요청 + Skill 카탈로그                │
│         (메타데이터 + 소스코드)              │
│   출력: {mode, skill, params/modifications}  │
└──────────────────────────────────────────────┘
        ↓
   ┌────┴────┬─────────┐
   ↓         ↓         ↓
[Mode A]  [Mode B]  [Mode C]
   │         │         │
   │         │         ↓
   │         │    ┌──────────────────────────┐
   │         │    │ Stage 1.5: Code Synthesis│
   │         │    │   외부 LLM이 변형 코드    │
   │         │    │   생성 → sandbox 실행     │
   │         │    │   (원본 skill 불변)       │
   │         │    └──────────────────────────┘
   │         │         ↓
   ↓         ↓         ↓
┌──────────────────────────────────────────────┐
│ Stage 2: Skill Execution                     │
│   - Mode A: 원본 skill                       │
│   - Mode B: 원본 + 수정 params               │
│   - Mode C: 변형 skill (sandbox)             │
└──────────────────────────────────────────────┘
        ↓
┌──────────────────────────────────────────────┐
│ Stage 3: Synthesis                           │
│   외부 LLM이 결과 + 변형 내용 종합           │
│   변형 적용 시 사용자에게 명시적으로 공개    │
└──────────────────────────────────────────────┘
        ↓
[최종 답변]
```

#### 모드별 상세

| 모드 | 트리거 | LLM 작업 | Skill 변경 | 위험도 | 예상 비율 |
|---|---|---|---|---|---|
| A | 표준 요청 | skill 선택만 | 없음 | 낮음 | 50~60% |
| B | 정형 변형 | skill 선택 + 파라미터 조정 | 없음 | 낮음 | 30~40% |
| C | 자유 변형 | 코드 수정 후 실행 | 임시 복제본 수정 | 높음 | 5~10% |

#### Skill 메타데이터 표준 (Case 1과 호환)

```python
SKILL_META = {
    "name": "noise_characterization",
    "description": "...",
    "params_schema": {
        "target": {"type": "str", "required": True},
        "roi": {"type": "list[int]", "default": None},
        "snr_threshold_db": {"type": "float", "default": 40.0},
    },
    "output_schema": {...},
    "modifiable": True,
    "modify_constraints": [
        "함수 시그니처 유지",
        "출력 스키마 유지",
        "계산 로직만 수정 가능",
    ],
    "examples": [...],
}
```

#### 데이터 외부 전송 정책

| 데이터 종류 | 전송 여부 |
|---|---|
| Raw 이미지/측정 원본 | ❌ 차단 |
| 측정 수치 결과 | ✅ 허용 |
| 정상범위/판정 | ✅ 허용 |
| 사용자 자연어 요청 | ⚠️ PII 필터 후 |
| Skill 카탈로그 메타데이터 | ✅ 허용 |
| 도메인 룰북 텍스트 | ⚠️ 정책에 따름 |

#### Mode C 안전 가드

| 가드 | 메커니즘 |
|---|---|
| Import 화이트리스트 | numpy, scipy, skimage 등만 허용 |
| 파일/네트워크 차단 | sandbox에서 fs/socket 제한 |
| 실행 시간/메모리 제한 | timeout, resource limit |
| 정적 분석 | AST 기반 위험 패턴 사전 탐지 |
| 변형 범위 제한 | 시그니처/스키마 유지 강제 |
| 결과 검증 | 출력 스키마 일치 검증 |
| 원본 불변 | 임시 복제본만 수정, 파일은 read-only |

#### Mode C 결과 공개 원칙

- 변형 코드로 측정한 경우 **변형 내용을 사용자에게 명시적으로 공개**
- 검증 엔지니어 도메인의 신뢰성에 직결되므로 필수

## 4. Case 1과 Case 2의 비교

| 항목 | Case 1 | Case 2 |
|---|---|---|
| 핵심 키워드 | 사전 정의 Pipeline | Mode 기반 Skill 운용 |
| LLM 호출 횟수 | 2~4회 (4B) | 1~3회 (외부) |
| Skill 입도 | 굵게 (절차형) | 굵게 + 파라미터화 |
| Plan 주체 | Skill 작성자 (사람) | 외부 LLM (런타임) |
| 라우팅 정확도 의존 | 매우 높음 | 낮음 (LLM이 조합) |
| 자유 요청 대응 | 불가 | 가능 (Mode B/C) |
| 디버깅 난이도 | 쉬움 | 중간 |
| 외부 의존성 | 0 | 네트워크 + API |

**두 시스템은 독립 구현하되, Case 2는 Case 1 skill을 메타데이터 추가로 재활용.**

## 5. 개발 우선순위

### Case 1

| 순위 | 작업 |
|---|---|
| 1 | Skill 카탈로그 설계 (입도 결정) |
| 2 | Skill 5~10개 구현 + 단위 테스트 |
| 3 | Stage 1 라우터 프롬프트 + few-shot |
| 4 | Stage 3 분석 프롬프트 + few-shot |
| 5 | Self-consistency 다수결 로직 |
| 6 | UNSURE 처리 / 사용자 확인 흐름 |

### Case 2 (Case 1 완성 후)

| Phase | 작업 | 산출물 |
|---|---|---|
| 1 | Skill 메타데이터 스키마 정의 | SKILL_META 표준 |
| 2 | 기존 skill에 메타데이터 추가 | Case 2 입력 준비 |
| 3 | Skill 파라미터화 강화 | Mode B 커버 영역 확대 |
| 4 | Mode A + B 구현 (tool-calling) | Case 2 80% 커버 |
| 5 | Sandbox 실행 환경 구축 | Mode C 인프라 |
| 6 | Mode C 구현 + 안전 가드 | Case 2 완성 |
| 7 | 모드 선택 라우터 튜닝 | 정확한 모드 분기 |

**Phase 4까지만 해도 실용 가치 큼.** Phase 5~6은 자유 변형 요청 빈도 데이터 확인 후 결정.

## 6. 핵심 권장사항 요약

| 권장 | 이유 |
|---|---|
| Case 1과 Case 2 독립 구현 | 통합 가정 없이 각자 최적화 |
| Skill 파라미터화에 집중 투자 | Case 2의 Mode B가 자유도 70% 흡수 |
| 원본 skill은 절대 불변 | Mode C도 임시 복제본만 수정 |
| Mode C 도입은 수요 확인 후 | 인프라 비용/위험도 고려 |
| 변형 적용 시 사용자에게 공개 | 검증 도메인 신뢰성 |
| 4B의 종합 추론에는 self-consistency | Case 1 분석 단계 품질 보완 |
| LLM에 자유 분해 시키지 않기 | 4B 한계의 가장 큰 함정 |

## 7. 폐기된 / 적용하지 않는 접근

| 접근 | 폐기 이유 |
|---|---|
| 트리/분할정복 멀티 에이전트 | 4B에 분해 맡기면 무너짐, 도메인이 정형이라 불필요 |
| 큰 모델 fallback 캐스케이드 | 로컬 단일 인스턴스 제약 (Case 1) |
| RAG | 사용자 제약 |
| LLM ReAct 자유 루프 | 4B에서 발산 위험, Case 1에 부적합 |
| Case 1과 Case 2 통합 시스템 | 사용자 결정으로 별개 구현 |
