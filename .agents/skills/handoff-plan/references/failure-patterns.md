# 설계 실패 패턴 — verify 자기 리뷰 + 설계 리뷰 전수 증거

`docs/handoff/*/verify.md` 142개의 「검증 자기 리뷰 → 설계 단계」 절과, **READY 직후 설계
리뷰에서 잡힌 결함**에서 **원문을 인용**해 패턴별로 묶었다. 추상 규칙만 주면 문자 그대로만
지키게 되므로, *왜* 그 규칙이 있는지 보이도록 문장을 남긴다.

**읽는 법**: SKILL.md 의 관문에서 막히거나 판단이 애매하면 해당 패턴의 원문을 읽어라.
자기 상황과 가장 닮은 사례를 찾는 것이 규칙을 외우는 것보다 낫다.

**갱신 관례**: 새 설계 실패가 나오면 — verify 자기 리뷰든, **READY 이후 설계 리뷰든, 구현
턴의 이견이든** — 해당 패턴에 한 줄 추가한다. 어느 패턴에도 안 맞으면 다음 번호로 신설한다.
**이 파일이 저장소의 설계 실패 축적 지점이다.**

> 통계: verify 142건 중 **r1 PASS 124건**. 절차 자체는 작동한다 — 아래는 나머지 구간에서
> 반복된 것들이며, 절차를 갈아엎으라는 뜻이 아니라 **이 지점들만** 막으라는 뜻이다.

> **P14~P16 은 0158 설계 리뷰(2026-08-03)에서 나왔다.** 이 건은 구현 전에 잡혀 라운드를

## P1 — 테스트 seam 을 설계가 지정하지 않음 (4건)

테스트 못 하는 형태로 착지한다.

- **0085**: "plan 이 AC9 에 '설치 핸들러 게이트 분기 테스트(autoUpdater 주입 mock)'를
  명시했으나, `UpdateController`/`computeUpdateInstallGate` 가 모듈 최상위에서
  `electron`(`app.getVersion`)·`send.ts`(webContents)를 import 하는 구조라 **순수 단위 테스트
  seam 이 부재**하다. 설계가 '주입 mock' 을 요구했으면 게이트 판정부를 electron 비의존 순수
  모듈로 분리하는 **seam 까지 지정했어야** 했다. → D1"
- **0118**: "판정 함수 배치를 chat-turn export 로 잡아 테스트 격리(electron import)를 놓쳤다 —
  구현 턴에서 조정(선조치 ✅). **다음부터 순수 함수는 처음부터 feature 슬라이스 배치를
  기본값으로**."
- **0078**: "plan 은 seed 경로 해석을 bootstrap 인라인 메서드로 두었으나, 구현자가
  testable seam(`resolveBuiltinSkillsDir`)으로 분리해 AC10 을 검증 가능하게 만들었다.
  plan 이 처음부터 '경로 계산 순수 분리'를 명시했다면 더 좋았을 것."
- **0157**: verify r1 이 `browser-session-store.ts` 를 "electron 의존이라 미테스트" 로 결론짓고

## P14 — 참조 구현의 커버리지를 계약의 커버리지로 착각 (2건)

실험·프로토타입·다른 브랜치의 코드를 설계 입력으로 쓸 때, **그 구현이 다룬 범위가 곧 계약의
범위라고 가정**해버린다. 참조 구현은 자기 한 가지 경우만 풀면 되지만 계약은 전부를 다룬다.

- **0158**(설계 리뷰): 실험이 Confluence PAT 하나만 다뤄 `begin → collect 1회 → binding` 이면
  끝이었다. 설계가 그 흐름을 그대로 옮겼는데, **계약(`contracts/auth-plugin.ts:138-150`)의
  `AuthStep` 은 `collect`·`browser`·`device_code`·`done`·`failed`·`not_supported` 6분기이고
  `continue` 는 반복 호출**이다. 브라우저 로그인·디바이스 코드 플로우가 설계에서 통째로 빠졌다.
- **0158**(설계 리뷰): 실험이 도구를 `create(ctx)` 팩토리로만 만들었는데, 설계는 여기에
  "registry 가 manifest 선언과 1:1 검증한다(0157 규칙 재사용)"를 얹었다. **그러나 registry 가
  검증하는 provider·connector 는 정적 `descriptor` 를 가진 객체**이고 `create(ctx)` 는 연결
  컨텍스트가 있어야 호출되므로 **등록 시점에 비교할 대상이 없다** — 시점상 성립 불가능한 설계였다.

> 체크: ⓐ 계약의 union/enum 멤버를 **전수 나열**하고 참조 구현이 각각을 다루는지 표시하라.
> ⓑ **기존 메커니즘을 "재사용한다" 고 쓸 때**, 새 대상이 그 메커니즘이 요구하는 *형상*(정적
> descriptor 등)과 *시점*(등록 시 / 연결 시 / 턴 시)을 만족하는지 확인하라. "재사용" 은
> 근거가 아니라 주장이다.

## P15 — 계약이 선언한 제약의 강제 지점을 지정하지 않음 (1건)

계약에 제약을 표현하는 필드가 있는데, **누가 언제 그것을 검사하는지** 설계가 말하지 않는다.
선언만 있고 강제가 없는 필드는 조용히 무력해진다.

- **0158**(설계 리뷰): `ConnectorDescriptor.acceptedAuthProviders`(`contracts/connector-plugin.ts:53`)
  가 "이 connector 가 받아들이는 auth provider 목록" 을 선언하지만, 설계 어디에도 **연결 시점에
  binding 의 provider 가 그 목록에 드는지 검사**하는 지점이 없었다. registry 의
  `validateCrossReferences`(`registry.ts:141-156`)는 provider 의 *존재*만 확인한다 — 즉 임의
  provider 로 임의 connector 에 붙는 조합을 막는 코드가 0이었다.

> 체크: 소비하는 계약의 **필드를 하나씩 훑으며** "이건 누가, 어느 순간 검사하나" 를 답하라.
> 답이 "아무도" 인 필드가 있으면 그게 구멍이다. 특히 allowlist·수용 목록·capability 선언처럼
> **부정형 제약을 표현하는 필드**가 새는 자리다.

## P16 — 유예가 공짜라고 오판 (1건)

결정을 후속 핸드오프로 미룰 때, **미루는 비용이 0인지** 따지지 않는다. 되돌릴 수 있는 결정과
한 방향으로만 열리는 문(one-way door)은 다르다.

- **0158**(설계 리뷰 r2→r3): 다중 연결 지원 여부를 Open Question 으로 올리며 "데이터 모델이
  이미 N:1 로 열려 있으니 나중에 규칙만 풀면 손해가 없다" 고 판단했고, 사용자에게도 **"어느 쪽이든
  이번 라운드 작업 내용은 같다"** 고 말했다. **틀렸다.** 데이터 모델은 맞았지만 **도구 이름이
  일방향**이었다 — 나중에 다중 연결을 풀면 첫 연결의 도구가 `jira_search` → `jira_search-hq` 로
  **개명**되고, 그 순간 대화 기록에 영속된 도구 이름이 무효가 되며 이름 기준 승인 설정이 헛돈다.
  즉 유예가 막으려던 파손을 유예 자체가 부르는 구조였다. 사용자가 실제 요구(Jira 서버 다수)를
  밝히고서야 드러났다.

> 체크: 무언가를 후속으로 미룰 때 **"나중에 하면 지금보다 비싼가"** 를 한 줄로 답하라.
> 특히 **이름·식별자·스키마·파일 포맷·공개 계약**은 일단 나가면 소비자가 생겨 개명 비용이
> 붙는다. 이런 것이 걸린 결정은 **미루지 말고 사용자에게 지금 물어라** — 물어보는 비용이
> 되돌리는 비용보다 항상 싸다.
