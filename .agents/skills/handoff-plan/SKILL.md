# 핸드오프 plan 작성

## 이 스킬의 위치

절차·상태 머신·역할 분담의 **정본은 `docs/handoff/AGENTS.md`**, 문서 뼈대는
`docs/handoff/_templates/plan.template.md` 다. **여기서 재서술하지 않는다** — 먼저 그 둘을 읽어라.

이 스킬은 그 위에 **검증 가능성 게이트**만 얹는다. AGENTS.md §"설계 시 담아야 할 것" 6항목은
*무엇을 쓸까* 를 말하지만 *쓴 것이 실제로 검증 가능한가* 를 강제하지 않는다. 이 저장소의
verify 문서 142개 중 14개 핸드오프가 FAIL 라운드를 겪었고, 그 자기 리뷰가 지목한 설계 실패는
같은 13개 패턴으로 반복된다. 아래 3개 관문이 그 13개를 막는다.

증거 원문(어느 핸드오프의 어떤 문장인지)은 [`references/failure-patterns.md`](references/failure-patterns.md).
**패턴 이름만 보고 넘기지 말고, 해당 관문에서 막히면 그 파일의 원문을 읽어라** — 규칙이 아니라
사례가 판단을 만든다.

## 순서

```
0. AGENTS.md + template 읽기 → INDEX.md 에서 find-or-create
1. 관문 1 — 착수 전 사실 확정      (plan 을 쓰기 *전*)
2. 초안 작성 (template 섹션 채우기)
3. 관문 2 — 인수 기준의 검증 가능성  ★ 최대 반복 지점
4. 관문 3 — 구현 가능성·테스트 가능성
5. self-review 체크리스트 → READY 표기 → INDEX.md 갱신 → 커밋
```

## 관문 1 — 착수 전 사실 확정 (P3·P5·P6·P9·P10·P12)

plan 을 쓰기 **전에** 확정하고, 결과를 `## 자료조사` 에 레퍼런스와 함께 남긴다.
여기서 아낀 30분이 구현 3라운드로 돌아온 사례가 있다(0134→0139→0141).

- **인용할 모든 수치를 그 자리에서 재측정한다**(P3). 선행 문서·이전 핸드오프의 숫자를
  승계하지 않는다. **내역의 합 = 총계인지 검산**한다(0157 은 승계한 채널 수가 이미 틀려 있었다).
  재측정이 불가능한 수치는 인수 기준에 쓰지 말고 **불변식으로 바꾼다**(0019).
- **전제는 실측한다**(P5). "아마 이럴 것" 을 설계 근거로 삼지 않는다. 진단성 작업이면
  **권위 신호를 먼저 정한다** — "무엇을 보면 이 가설이 틀렸다고 판정할 수 있는가". 0128 은
  단일 로그로 성급 단정했다가 진단 로그(`message.model`·비용 증분)를 확보하고서야 진상을 봤다.
- **외부 규약은 1차 출처로 대조한다**(P6) — SDK `d.ts`, npm 패키지 실물, 공식 문서.
  **사용자가 "확인했다" 고 말한 것도 별도로 대조한다**(0117 은 그래서 r2 로 되돌아갔다).
- **"조사 불가" 를 선언하기 전에 한 번 더 시도한다**(P12). 0150 은 `node_modules` 부재를
  제약으로 받아들였는데 구현 턴에 `npm ci` 하니 바로 됐고, 그 사이 *문제 서술 자체가 틀린 채로*
  설계가 진행됐다. 0156 은 "확인 불가" 로 적은 옵션을 타입 정의를 읽어 근거를 댈 수 있었다.
  환경 제약(egress 차단 등)도 **기정사실로 깔지 말고 먼저 탐지하고 조건부로** 적용한다(0147).
- **선행 자료를 비판적으로 검토한다**(P9). 인용하는 연구·보고서·이전 핸드오프의 주장을
  실제 코드와 대조한다. 특히 ⓐ 이 요구가 *달성 가능한가* ⓑ 이 요구가 *실재하는가*
  ⓒ "현행 구현" 이라 적힌 것이 정말 코드에 있는가.
- **기존 채택 결정과의 충돌을 찾는다**(P10). `git log`·AGENTS.md·`docs/arch/**` 에서 이번 변경이
  뒤집는 결정을 찾아 표로 적는다. 뒤집으면 근거를, 유지하면 유지 사실을 적는다.
  **기존 테스트가 잠가둔 계약**도 여기 포함된다 — 0153: "0152 verify 의 '회귀 0' 은 기존 테스트가
  옛 계약을 통과시켰기 때문이지 정합했기 때문이 아니다. *테스트 green ≠ 계약 정합*."

## 관문 2 — 인수 기준의 검증 가능성 (P2·P8·P11) ★

**여기가 이 스킬의 핵심이다.** 자기 리뷰가 가장 많이 지목한 지점이고, FAIL 라운드의 직접
원인이 대부분 여기다.

인수 기준 표에 **`검증 수단` 열을 필수화**하고, 각 칸을 `파일::케이스` 로 적는다(0098 관례).

| # | 인수 기준 | 검증 수단 |
|---|---|---|
| 1 | … | `app/src/main/features/x/y.test.ts::"…"` |

### 규칙

1. **검증 수단 칸을 채울 수 없으면 기준이 잘못 쓰인 것이다.** 다시 쓴다. 진짜로 기계 검증이
   불가능하면(시각·실기·레이스) 칸에 **"런타임 실기로만 확인 가능 — 사람"** 이라고 *명시*한다.
   0150: "기계 검증 가능한 형태로 못 쓸 사정은 있었으나, **그렇다면 인수 기준에 그렇게
   명시했어야** 한다."
2. **부정형·"불변" 기준을 금지한다.** "거부 흐름 불변" 은 *기존 거부 자체가 결함*일 때
   통과처럼 보인다(0047 — 6라운드를 태웠다). "거부 시 deny 가 모델에 도달한다" 같은
   **양성 단언**으로 바꾼다.
3. **현행 코드가 이미 통과하는 기준은 측정력이 0이다.** 기준을 쓴 뒤 "지금 코드가 이걸
   통과하나?" 를 물어라. 통과하면 다시 쓴다.
4. **AC 끼리 모순되지 않는지 본다**(P11). 0149 는 AC6 이 자기 plan 의 AC16 과 자가당착이었고
   "체크리스트에 'AC 간 충돌 없음' 항목이 없다" 고 적었다. 0151·0148 도 같은 실패.
   **자기 산출물이 자기 AC 를 위반하는 경우까지** 본다(0148 — "범위 절 무변경" AC 가 자기가
   만드는 새 파일과 충돌).
5. **목적을 AC 안에 둔다.** "X 를 포함한다" 로 멈추지 말고 "그래서 Y 가 된다" 까지 적는다.
   0150 의 AC6 은 응답 필드 포함까지만 요구해, 정작 작업 목적("카드 없이 편집이 진행되는가")이
   기준 밖으로 밀려났다.
6. **파라미터는 단위를, 이중 케이스는 union 을**(P8). 0055: "정책 파라미터의 *단위*를
   **시그니처 주석까지** 못 박을 것"(capacity 가 전체 cap 인지 idle cap 인지 모호해 이견 발생).
   0056: 이중 케이스는 flat 객체가 아니라 discriminated union 으로.
7. **도달 가능성을 확인한다.** 0149: AC10 이 "세션 teardown 경로에서 clear" 를 요구했는데
   그 상태가 클로저에 갇혀 도달 불가였다 — 조사 단계에서 알 수 있었다.

## 관문 3 — 구현 가능성·테스트 가능성 (P1·P4·P7·P13)

- **신규 모듈마다 `테스트 방법`을 적는다**(P1). electron/DB/네트워크에 닿으면 **순수부 분리
  seam 을 설계에 포함**한다. 0085: "게이트 판정부를 electron 비의존 순수 모듈로 분리하는
  **seam 까지 지정했어야** 했다." 0118: "다음부터 순수 함수는 처음부터 feature 슬라이스 배치를
  기본값으로."
  **"테스트 불가" 로 적으려면 *무엇을 떼면 가능한가* 를 먼저 답한다** — 0157 은 이 질문을
  verify r2 에서야 물었고, 떼어보니 가능했을 뿐 아니라 이중 구현까지 드러났다.
- **조사는 대표 샘플 + 전수 grep 수치를 함께 적는다**(P4). 0121: "'대표 샘플' 조사의 한계 …
  향후 plan 은 대표 샘플 + **전수 grep 수치**를 함께 요구할 것." **"N곳 발견" 의 N 이 없으면
  조사가 끝나지 않은 것**이다. 상태 전이·마이그레이션 등록처럼 *빠뜨리면 조용히 깨지는*
  지점은 특히 전수(0119 inflight 전이 지점 / 0129 마이그레이션 5-지점).
- **저장소의 기존 규칙을 설계 입력으로 읽는다**(P7):
  - `app/eslint.config.mjs` — `boundaries`(레이어 DAG·feature 교차 금지) + react hooks 규칙
    (0082·0150 은 lint 규칙을 안 보고 설계해 왕복을 샀다)
  - 위생 테스트 — `resources.test` 류의 빈 값 금지 등(0097: "**위생 테스트 규칙도 설계
    입력으로 읽을 것**")
  - 마이그레이션 append-only 가드(`scripts/check-migrations-appendonly.mjs`)
  - preload/renderer 의 기존 호출 관례(0123 — fire-and-forget vs invoke 패스-스루)
  - 신규 타입·모듈마다 **어느 레이어에 두고 누가 import 하는가** 를 미리 적는다.
- **라이프사이클·취소·전이를 파생 UX 에서 펼친다**(P13). quit/crash/renderer-gone(0046),
  취소 신호·draining(0067), 모드 전이 직후의 중간 상태(0099), 창 닫힘·타임아웃(0130).
  템플릿의 예시를 복붙하지 말고 **이 작업에 실제로 해당하는 것만** 적는다.

## READY 전 self-review

템플릿의 6항목 체크리스트에 더해, 아래는 **기계적으로 확인 가능하므로 반드시 본다**:

- [ ] 인수 기준 표의 **`검증 수단` 칸이 하나도 비어 있지 않다** (기계 검증 불가 항목은
      "사람 실기" 로 *명시적으로* 채워져 있다)
- [ ] 부정형/"불변" 기준이 0개다 (전부 양성 단언)
- [ ] **AC 끼리 모순이 없다** — 각 AC 를 다른 AC 와 짝지어 훑는다
- [ ] 인용한 수치를 **이번 세션에서 직접 측정**했다 (승계한 숫자 0개)
- [ ] 신규 모듈마다 테스트 방법이 적혀 있고, electron/DB 의존이면 순수부 seam 이 설계에 있다
- [ ] 전수 조사 대상에 **N 수치**가 적혀 있다

하나라도 ❌면 `plan/READY` 로 표기하지 않는다.

## 마무리

- `docs/handoff/INDEX.md` 행 갱신(`plan/READY`, 다음 주체) — 기능 구현이면 Codex,
  리팩토링·버그수정이면 Claude 가 그대로 구현까지.
- 커밋: `docs(handoff): <slug> 설계` + trailer(`Agent: claude` · `Handoff: docs/handoff/<NNNN-slug>/`
  · `Status`). 형식 정본은 `docs/git-template.md`.

## verify/FAIL 후 plan 을 고칠 때

- 미해결 항목은 템플릿의 **`[검증자 기입] 파생 이슈`** 챕터로 이관한다(plan 상단을 다시 쓰지 않는다).
- **FAIL 을 부른 AC 는 관문 2 를 다시 통과시킨다** — 대개 그 AC 가 측정 불가였던 것이 원인이다.
- 라운드가 3을 넘으면 INDEX.md 에 에스컬레이션을 표기하고 사용자에게 묻는다(AGENTS.md).
  0141(3회 반복)의 근본 원인은 **잘못된 귀속 가설을 라운드마다 재사용한 것**이었다 — 라운드가
  반복되면 수정안이 아니라 **전제**를 의심하라.
