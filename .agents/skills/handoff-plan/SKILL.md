# handoff-plan — 현재 작업의 설계 정본 만들기

## 책임

이 스킬은 **이번 작업의 plan을 정확하게 만드는 실행 스킬**이다.

- 앞부분은 **Product & UX Contract**다. UI가 없는 작업도 사용자가 관측할 동작·외부 계약·운영 행위를 여기서 먼저 고정한다.
- 뒷부분은 **Technical Design**이다. 코드베이스 사실, 아키텍처, 데이터/제어 흐름, 모듈 책임, 테스트 방법을 구현자가 바로 작업할 수 있을 정도로 구체화한다.
- 현재 요구를 비판적으로 검토하는 책임은 유지한다. 과거 실패를 분석해 이 스킬 자체를 고치는 메타 책임은 [`../handoff-review/SKILL.md`](../handoff-review/SKILL.md)에 위임한다.

**하지 않는 일**:

- `references/failure-patterns.md`를 매 plan마다 읽고 사례를 즉석에서 일반화하지 않는다.
- verify 결과를 보고 여기서 새로운 실패 패턴을 누적하거나 SKILL을 자기 수정하지 않는다.
- 여러 턴 뒤 최신 대화만 보고 앞선 확정 결정을 조용히 덮어쓰지 않는다.

과거 사례는 `handoff-review`가 **지침 변경 후 회귀 검증**에 사용한다. 이 스킬의 실행 정본은 현재 `SKILL.md`다.

## 먼저 읽을 것

1. `docs/handoff/AGENTS.md` — 상태 머신·역할·find-or-create.
2. `docs/handoff/INDEX.md` — 이어갈 handoff가 있는지 확인.
3. [`plan.template.md`](plan.template.md) — 문서 뼈대.
4. 현재 작업과 직접 관련된 코드·계약·문서·대화 기록.

## 작성 순서

```text
0. find-or-create + 기존 plan/대화 기록 읽기
1. Decision Ledger 복원/갱신
2. Product & UX Contract 초안
3. 요구 비판적 검토 + 필요한 사용자 질의 판정
4. 코드·계약·외부 규약 조사
5. Product & UX Contract 확정 + Acceptance Criteria 작성
6. Technical Design 작성
7. 검증 가능성·구현 가능성 게이트
8. 문서 전체 정합성 검사
9. READY self-review → INDEX 갱신
```

문서에서는 Product/UX가 앞에 오지만 **근거 없는 제품 판단을 만들라는 뜻이 아니다**. 조사로 사실을 닫은 뒤 앞부분을 확정한다.

# 1. Decision Ledger — 여러 턴의 합의를 잃지 않는다

plan을 새로 만들거나 갱신할 때 가장 먼저 현재 대화·기존 plan에서 **결정 단위**를 뽑는다.

- `ACTIVE` — 현재 구현이 따라야 하는 결정.
- `SUPERSEDED` — 후속 사용자 결정으로 명시적으로 대체됨. 대체 Decision ID를 연결한다.
- `OPEN` — 사용자 결정이 아직 필요함.

## 반드시 결정으로 잡는 것

- 사용자가 “A로”, “그대로”, “제거”, “유지”, “이 경우에는”, “~할 수 있다면”처럼 방향·조건·이유를 지정한 문장.
- UI 배치·상태·취소·전환·표시 규칙처럼 구현 세부처럼 보여도 사용자가 직접 합의한 UX.
- 이름·식별자·스키마·외부 계약·저장 형식처럼 나중에 바꾸기 비싼 one-way door.
- 이전 턴의 선택지를 사용자가 재확인하거나 변경한 내용.

## 갱신 규칙

1. 새 턴이 오면 **기존 ACTIVE 결정과 새 요청을 먼저 diff**한다.
2. 충돌하지 않으면 기존 결정은 남는다. 최신 턴에 다시 언급되지 않았다는 이유로 삭제하지 않는다.
3. 사용자가 명시적으로 바꿨다면 기존 항목을 `SUPERSEDED`로 바꾸고 새 항목을 만든다.
4. 변경인지 보완인지 불명확하고 결과가 달라지면 사용자에게 묻는다.
5. 이유·조건절도 계약 일부다. “제거”를 “다른 곳으로 이동”으로 바꾸는 식의 재해석을 금지한다.

Decision Ledger가 Product/UX Contract와 Technical Design보다 우선한다. 본문이 ACTIVE 결정과 충돌하면 본문이 잘못된 것이다.

# 2. Product & UX Contract — 코드보다 먼저 사용자가 받는 결과를 고정한다

UI 작업만을 뜻하지 않는다. renderer가 없어도 CLI/API/저장/운영자/외부 구현자가 관측하는 동작은 제품 계약이다.

반드시 다음을 적는다.

- **목표와 문제**: 무엇이 불편하거나 잘못됐고 완료 후 무엇이 달라져야 하는가.
- **명시 요구 vs 해석**: 사용자 문장과 설계자의 추론을 분리한다.
- **동작 흐름**: 사용자 시작 행동/시스템 이벤트 → 중간 상태 → 성공/실패 결과.
- **상태와 전이**: loading/empty/error/cancel/retry/close/restart/concurrency 등 실제 관련 상태만.
- **범위/비범위**: 비범위가 범위의 실행을 막지 않는지 확인한다.
- **용어/이름**: UI·외부 계약에 새 이름을 노출하면 기존 의미와 충돌하는지 조사한다.
- **Acceptance Criteria**: 구현 방법이 아니라 관측 가능한 결과를 먼저 쓴다.

## 사용자에게 다시 물어야 하는 경우

- 두 해석 모두 합리적이고 **사용자가 받는 결과가 달라진다**.
- 이름·식별자·스키마·공개 계약처럼 미루면 비용이 커진다.
- 제품 의도·정책·신규 의존성처럼 에이전트가 단독으로 정할 수 없다.
- 이전 ACTIVE 결정과 새 요청이 충돌하지만 사용자가 변경 의사를 명시하지 않았다.

코드 조사로 닫을 수 있는 사실은 사용자에게 묻지 말고 조사한다.

# 3. 요구 비판적 검토

설계 전에 다음을 확인한다.

- **증상과 원인**: 요구가 진짜 원인을 겨냥하는가. 권위 신호를 정하고 실측한다.
- **이미 충족됐는가**: 기존 코드로 이미 되는 기능을 다시 만들지 않는다.
- **더 작은 해법이 있는가**: 구조 변경 없이 목표를 달성할 수 있는지 본다. 단 “제거/정리” 요구는 **그 능력 자체가 없어도 되는지**도 묻는다. 이동은 제거가 아니다.
- **선행 자료가 맞는가**: 이전 handoff·보고서·가이드의 주장을 코드와 다시 대조한다.
- **기존 결정과 충돌하는가**: docs뿐 아니라 코드 주석·계약 헤더·테스트가 잠근 결정을 찾는다.

이견은 근거와 우려를 적되 작업 회피에 쓰지 않는다. 어떤 가정으로 진행해도 제품 결과가 달라지는 결정만 사용자에게 올린다.

# 4. 조사 게이트

## 증거 우선순위

- 현재 코드·테스트·타입·계약.
- 저장소 정본 문서.
- 외부 SDK/API는 벤더 1차 문서·실제 패키지 타입/런타임.
- 저장소 내부 과거 관찰·주석은 보조 근거.

외부 API에서 1차 문서와 내부 관찰이 충돌하면 **동일 배포·동일 endpoint·동일 method라는 증거가 없는 한 1차 문서를 기본값**으로 둔다.

## 조사 규칙

- 숫자는 승계하지 말고 이번 세션에서 다시 센다. 총계는 내역 합과 검산한다.
- “유일한/항상/절대” 같은 전칭 표현은 `rg`로 반례를 전수 확인한다.
- 대표 샘플만 보지 않는다. 상태 전이·등록·마이그레이션·소비처처럼 빠지면 조용히 깨지는 표면은 **전수 grep + N개**를 남긴다.
- 기존 테스트를 검증 수단으로 인용하면 파일뿐 아니라 **케이스/핵심 동작이 실제 존재하는지** 확인한다.
- 문서의 `§표제어`나 “확정 결정”을 인용하면 내부 앵커가 실제 존재하는지 grep한다.
- 하위 가이드의 주장을 정본으로 승격할 때는 코드에서 재검증한다. 틀렸다면 승계 원본도 함께 고친다.
- **작업 관련 저장소 규칙을 설계 입력으로 읽는다**: `eslint` boundaries/hooks, 위생 테스트, migration append-only guard, preload/renderer 호출 관례, 디렉토리 `AGENTS.md` 등. “코드가 컴파일된다”와 “이 저장소 규칙에 맞는다”를 분리한다.

# 5. Acceptance Criteria 게이트 — 의미를 검증한다

각 AC에는 `동작 기준 / 검증 수단 / 프로덕션 도달 경로`가 필요하다.

- 부정형 “불변/문제 없음/0건”만으로 목적을 표현하지 않는다. 필요한 정상 동작을 쓴다.
- 테스트 **파일명**을 계약으로 만들지 않는다. 구현자가 파일을 옮겨도 검증 가능한 행동 단언이 정본이다. 기존 테스트 재사용 시 현재 케이스 존재를 확인한다.
- structural proxy가 semantic 목표를 대신하지 못한다. “함수 1회 호출”, “Promise.all 존재”, “시그니처가 X”가 목표 의미를 실제 보장하는지 적대 사례를 생각한다.
- **게이트의 완료 조건도 같은 대상이다.** “산출 전건이 N버킷으로 분류되고 미분류 0” 은 *분류했는가* 를 세지 *각 단언이 참인가* 를 세지 않는다. 완료 조건이 세는 것과 목표가 묻는 것이 다르면 그 차이를 §10 `실패 의미` 칸에 적는다 — 게이트가 초록인 채로 남는 결함이 그 차이만큼이다.
- `N회`·총량 식을 쓰면 **sink 를 부르는 프로덕션 호출부를 전수 검색으로 세어 식의 항에 매핑한 뒤** 관측 지점을 적는다. 호출 지점 grep과 sink 총호출 횟수는 다르고, 관측 지점이 그 호출부 일부만 모형하면(테스트 fake 등) 나머지 항은 반증될 수 없다 — 그때는 단언 범위를 그 관측 주체가 스스로 내는 호출로 좁힌다. 0194: `P + K + 1` 을 부팅 총량으로 적었으나 같은 `pushConnectionState` 를 회복 성공 경로가 2회 더 부르고, fake 는 그 항을 모형하지 않는다.
- 순서를 요구하면 단계 훅·순서 로그·주입 가능한 경계 등 **순서를 관측할 방법**도 설계한다.
- 사람 실기는 시각·실제 외부환경에만 쓴다. 목록 포함 여부·후보 계산·상태 파생 같은 로직은 순수 테스트 대상으로 내린다.
- 선택적 필드는 `true/false/undefined` 의미를 확인한다. 권한/보안은 미지정이 fail-open 되지 않게 한다.
- 외부 SDK로 넘기는 값은 필드 목록이 아니라 **SDK가 요구하는 타입/의미**를 AC로 잠근다. `as any`/`as never`가 필요한 경계는 별도 계약 테스트 후보다.
- 참조 fixture/example이 구현자를 안내한다면 그것도 계약을 만족해야 한다.

## 수치·총량·음성 게이트

- 줄 수/파일 수/모듈 수 같은 구조적 목표는 대상의 단계 지도를 먼저 그리고 **달성 가능한 이유**를 적는다. 추정이 어렵다면 상대 목표를 쓴다.
- 총량 임계는 제거 대상과 허용 대상이 섞이지 않았는지 형태별로 분해한다.
- `rg ... = 0` 같은 음성 게이트는 이력·허용 예외를 먼저 열거하고 술어에서 제외한다.
- AC가 25건을 넘으면 handoff/구현 단위를 분할할 수 있는지 먼저 검토한다.

# 6. Technical Design — 구현자가 바로 작업할 수 있게 쓴다

Product/UX Contract가 **무엇을** 정했다면 여기서는 **어떻게**를 정한다.

반드시 포함한다.

- 현재 코드 흐름과 변경 후 흐름. 필요하면 ASCII data/control flow.
- 레이어·모듈별 책임과 import 방향.
- 변경/신규 타입·함수·포트·IPC/API 계약.
- 생산자 → 정규화/상태 → 소비자의 end-to-end 경로.
- lifecycle/cleanup/cancel/retry/error propagation.
- 저장·마이그레이션·하위 호환성.
- 테스트 seam과 테스트 종류.
- 변경 파일과 각 파일의 역할.

## 구현 가능성 방어선

- electron/DB/native 의존 모듈의 순수부를 테스트해야 하면 **같은 파일 함수가 아니라 import graph가 끊긴 별도 파일 seam**까지 지정한다.
- 정책 파라미터는 **단위·범위·의미**를 계약/시그니처 수준에서 고정한다. 서로 배타적인 상태/대상은 불가능 조합을 허용하는 flat flags보다 **discriminated union**을 우선한다.
- “같은/동일한 규칙”을 여러 레이어가 쓰면 SSOT 위치와 강제 방법을 지정한다. 복붙 정규식은 금지한다.
- 참조 구현·fixture·다른 브랜치를 설계 입력으로 쓰면 **계약의 union/enum 멤버를 전수 나열**하고 참조 구현이 각각을 다루는지 coverage를 표시한다. 참조 구현의 범위를 계약 전체로 가정하지 않는다.
- 기존 메커니즘을 “재사용”한다고 쓸 때 새 대상이 요구 형상과 적용 시점을 만족하는지 확인한다.
- 계약 제약 필드는 **누가·언제 강제하는지** 적는다. 선언만 있고 enforcement point가 없으면 미완성이다. **지점이 여럿이면 전부 나열한다** — 하나만 적으면 구현도 하나만 닫는다.
- **한 동작이 저장소를 둘 이상 쓰면 그 사실을 먼저 적는다.** 원자적으로 함께 쓸 수 없는 저장소(파일 + 키체인, DB + 외부 API 등)를 순서대로 쓰는 동작은 **사이에서 죽었을 때 무엇이 관측되는지**가 설계 사항이다. "실패하면 보존한다" 같은 목표 문장은 그 질문에 답하지 않는다 — 쓰기 지점을 나열하고, 각 지점 실패 시의 관측 상태를 적고, 그 조합 중 허용 불가한 것이 있으면 설계로 없앤다(순서 교체·포인터 교체·2단 쓰기 등). **산출물이 문서인 작업도 대상이다** — 같은 판정·상태가 산출 문서와 `INDEX.md` 보드처럼 두 곳에 살면 그것도 두 곳 쓰기이고, 함께 갱신되지 않으면 두 사본이 서로 다른 말을 한다. 그런 사본이 있으면 §10 강제 지점에 **사본 전부**를 지점으로 적는다.
- 부팅/초기화에서 레지스트리·스토어 값을 새로 늘리면 기존 **모든 소비처를 전수 나열**하고 값 증가의 영향을 확인한다.
- 로그/경고/중복 오류 같은 증상을 없앨 때 그 증상이 가리던 **실제 상태 변화가 남는지** 확인한다.
- 표시 계약은 producer 기준과 consumer 파생 규칙을 쌍으로 설계한다. 파생 가능한 합성값으로 소비자가 정본을 우회하지 않게 한다.
- 모델 컨텍스트·네트워크 요청·배치 처리를 늘리면 **원천 상한 × 배치 상한**으로 worst-case 출력 길이/요청 수를 계산한다.
- 캐시·snapshot·hoisting·호출 축소 같은 최적화는 “덜 하면서 잃는 부수 효과”를 적고 회귀 테스트로 만든다.

## 외부가 구현하는 포트/계약

배포·플러그인·외부 구현자가 구현할 port/schema/config를 만들거나 바꾸면 그 계약 문서가 실제 진입 경로다. AC에 두 층을 모두 둔다.

- **shape**: 문서 예제가 실제 타입에 대입되어 typecheck 가능한가.
- **semantics**: 성공/실패/null/재시도 의미가 contract test와 일치하는가.

시그니처가 안 바뀌어도 구현자의 행동이 달라지는 의미 변경이면 문서를 같이 갱신한다.

# 7. 문서 정합성 게이트

본문을 다 쓴 **후** 수행한다.

1. Decision Ledger의 모든 `ACTIVE` 항목이 Product/UX·**AC**·Technical Design에서 유지되는지 확인한다. **AC가 ACTIVE Decision의 반대를 요구하면 그것은 문서 결함이다.**
2. 같은 대상(수명주기·식별자·상태·연결 수·오류 의미)을 여러 절이 서술하면 나란히 읽어 충돌을 찾는다.
3. Product/UX의 각 핵심 동작이 Technical Design의 실제 경로와 AC에 연결되는지 추적한다.
4. 기존 결정·규칙 표는 본문을 훑은 뒤 마지막에 채운다. **실제 본문 문장** 기준으로 유지/변경을 판정한다.
5. 인용 경로·문서 앵커·기존 테스트 케이스가 실제 존재하는지 확인한다.
6. 범위/비범위가 사람 실기나 프로덕션 도달 경로를 스스로 막지 않는지 확인한다.

**교차검증 결과는 관측으로 남긴다.** 체크박스 `[x]`는 검사를 수행했다는 증거가 아니다 — 1의 결과는 Ledger 갱신 메모에 `ACTIVE 결정 ↔ AC 대조: 충돌 0` 또는 `D-00N ↔ ACn (판정)` 한 줄로 적고, 2·5는 대조한 문장·경로를 인용한다.

> 사례(0190). READY self-review 전 항목이 `[x]`인 상태로 plan 결함 3건이 구현 턴까지 갔다 — AC8이 "배포 확장점 제거"를 요구했는데 D-005는 "문서화된 배포 확장점은 지우지 않는다"였고(정면 모순), AC1은 호출 지점과 sink 호출 횟수를 섞었고, AC14 주의사항은 사실이 틀렸다. 셋 다 위 1·2가 담당하는 축이다.

# 문서 문장 규칙

[`docs/handoff/AGENTS.md §산출물 문장 규칙`](../../../docs/handoff/AGENTS.md)을 따른다 — 판정 먼저, 주장 한 줄에 관측 하나, 표 한 칸 3줄, 문단 3문장. plan에서 특히:

- Part I과 Part II에 같은 사실을 두 번 쓰지 않는다. Part I은 관측 결과, Part II는 경로·계약이다.
- 조사 결과는 서술이 아니라 `대상 / 검색 / N / 의미` 표로 적는다.
- 길이를 줄이는 대상은 서술이다. AC·강제 지점·전수 개수·재현 수단은 줄이지 않는다.
- **사용자 문장의 이유·조건절은 요약하지 않고 원문으로 인용한다** — 조건절이 대안을 지정하는 경우가 있다(0183: "다른 feature 에서 api 를 쓸 수 있다면 … 모두 제거하라"를 배경으로 읽고 *이동*을 구현했다).

## verify/FAIL 후 plan 갱신

FAIL의 미해결 항목은 `[검증자 기입] 파생 이슈`에 누적한다. Product/UX Contract나 Decision Ledger를 실패 때마다 처음부터 다시 쓰지 않는다.

- **검증자가 `규범 정정 필요`로 표시한 파생 이슈는 재구현 전에 여기서 닫는다.** 그 표시는 verify가 §10 행 신설·AC 문면 정정처럼 구현자 권한 밖의 수정을 요구했다는 뜻이다 — 정정하거나, 정정하지 않는 근거를 그 행에 적어 요구를 종결시킨다. 어느 쪽도 하지 않고 구현자에게 넘기면 그 요구는 다음 라운드에 소멸한다(0198 r4→r5).
- 구현 결함이면 파생 이슈로 좁혀 재구현한다.
- 설계 계약이 틀렸다는 증거가 생기면 관련 Decision/AC/Technical Design만 명시적으로 수정하고 변경 이유를 남긴다. **고쳐 쓴 AC 행은 §5 AC 게이트와 READY self-review의 AC 항목을 다시 통과시킨다** — 최초 작성만 게이트를 받고 정정은 안 받으면 세 라운드째 틀린 기준으로 채점한다(0194 AC18: 대리 기준 → 정정한 닫힌 식이 조건부 항을 빼먹어 저장소의 테스트가 그것을 반증했다).
- 사용자 결정 변경이면 기존 Decision을 `SUPERSEDED` 처리한다. 실패로 위장하지 않는다.
- 반복 라운드에서 같은 종류가 다시 나오면 `handoff-review` 대상 신호로 올린다. **여기서 failure-patterns를 직접 갱신하지 않는다.**

## 마무리

`docs/handoff/INDEX.md`를 `plan/READY`와 다음 주체로 갱신하고 커밋 형식은 `docs/git-template.md`를 따른다.

**plan의 규범 행을 바꾸는 커밋은 구현 산출과 같은 커밋에 담지 않는다** — Decision·AC·§10 강제 지점이 규범 행이고, `plan/READY` 커밋도 verify/FAIL 후 정정도 같다. 설계자와 구현자가 같은 에이전트여도 마찬가지다 — verify §0의 기준선 잠금은 "구현 전 plan"을 diff로 꺼낼 수 있을 때만 작동하고, 한 커밋에 섞이면 구현자가 자기 산출에 맞춰 기준을 고쳤는지 아무도 확인할 수 없다(0189 r1 · 0194 r3 실측).
