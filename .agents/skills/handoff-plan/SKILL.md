# handoff-plan — 이번 작업의 설계 정본을 만든다

## 무엇을 위해 하는가

plan은 구현과 검증이 공유하는 **유한한 계약**이다. AC 동작 기준 · §10 자리 목록 · pair path · 규칙 칸의 분기 · 등록 변이 · 운영 gate · 선언 경계처럼 항목으로 적은 것(열거 원문)이 그 계약이다.

- verify는 열거 원문을 라운드 제한 없이 끝까지 지킨다. 열거되지 않은 것은 verify 1·2회째의 확장 창에서만 다룬다(`docs/handoff/AGENTS.md §판정 범위와 운영 gate`). 그래서 **여기서 열거한 것이 만들어지고 잠기는 것이다** — 빠진 것은 창이 닫히면 후보 표로 간다.
- 앞부분 **Product & UX Contract**는 사용자·소비자가 받는 결과를 먼저 고정한다. UI가 없는 작업도 관측할 동작·외부 계약·운영 행위를 여기서 정한다.
- **V**(`R↔AT`·`SD↔ST`·`AR↔IT`·`MD↔UT`)는 계약과 검증 증거를 잇는다. 명시적인 기존 V가 없으면 Baseline V, 기존 V를 일부 바꿀 때만 Delta V를 쓴다(`docs/handoff/AGENTS.md §공통 V 추적 프로토콜`).
- 뒷부분 **Technical Design**은 코드베이스 사실·아키텍처·흐름·모듈 책임·테스트 방법을 구현자가 바로 작업할 수 있을 만큼 구체화한다.
- 현재 요구를 비판적으로 검토하는 책임은 여기 있다.

하지 않는 일: `references/failure-patterns.md`를 매 plan마다 읽고 사례를 즉석에서 일반화하지 않는다. verify 결과로 실패 패턴을 누적하거나 이 SKILL을 고치지 않는다(그것은 [`../handoff-review/SKILL.md`](../handoff-review/SKILL.md)의 몫이다). 최신 대화만 보고 앞선 확정 결정을 덮어쓰지 않는다.

## 먼저 읽을 것

1. `docs/handoff/AGENTS.md` — 상태 머신·역할·find-or-create·발견 분류와 확장 창.
2. `docs/handoff/INDEX.md` — 이어갈 handoff가 있는지, 그리고 `## 새 handoff 후보` 표에서 이번 작업이 건드리는 파일·모듈과 겹치는 행.
3. [`plan.template.md`](plan.template.md) — 문서 뼈대.
4. 현재 작업과 직접 관련된 코드·계약·문서·대화 기록.

## 작성 순서

```text
0. find-or-create + 기존 plan/대화 기록 읽기
1. Decision Ledger 복원/갱신
2. Product & UX Contract 초안
3. 요구 비판적 검토 + 필요한 사용자 질의 판정
4. 코드·계약·외부 규약 조사
5. Product & UX Contract 확정 + Acceptance Criteria 작성
6. Baseline V 또는 Delta V 노드·pair·§10·선언 경계·적용 gate 확정
7. Technical Design 작성
8. 검증 가능성·구현 가능성 게이트
9. 문서 전체 정합성 검사
10. READY self-review → INDEX 갱신
```

문서에서 Product/UX가 앞에 오지만 근거 없는 제품 판단을 만들라는 뜻이 아니다. 조사로 사실을 닫은 뒤 앞부분을 확정한다.

# 1. Decision Ledger — 여러 턴의 합의를 잃지 않는다

plan을 만들거나 갱신할 때 가장 먼저 현재 대화·기존 plan에서 결정 단위를 뽑는다. 상태는 `ACTIVE`(지금 따를 결정) · `SUPERSEDED`(후속 사용자 결정으로 명시 대체 — 대체 ID 연결) · `OPEN`(사용자 결정 필요)이다.

반드시 결정으로 잡는 것:

- 사용자가 "A로"·"그대로"·"제거"·"유지"·"이 경우에는"·"~할 수 있다면"처럼 방향·조건·이유를 지정한 문장.
- UI 배치·상태·취소·전환·표시 규칙처럼 구현 세부로 보여도 사용자가 직접 합의한 UX.
- 이름·식별자·스키마·외부 계약·저장 형식처럼 나중에 바꾸기 비싼 one-way door.
- 이전 턴의 선택지를 사용자가 재확인하거나 변경한 내용.

갱신 규칙:

1. 새 턴이 오면 기존 ACTIVE 결정과 새 요청을 먼저 diff한다.
2. 충돌하지 않으면 기존 결정은 남는다. 최신 턴에 다시 언급되지 않았다는 이유로 지우지 않는다.
3. 사용자가 명시적으로 바꿨으면 기존 항목을 `SUPERSEDED`로 바꾸고 새 항목을 만든다.
4. 변경인지 보완인지 불명확하고 결과가 달라지면 사용자에게 묻는다.
5. 이유·조건절도 계약이다. "제거"를 "다른 곳으로 이동"으로 바꾸는 식으로 재해석하지 않는다(0183).

Decision Ledger가 Product/UX Contract와 Technical Design보다 우선한다. 본문이 ACTIVE 결정과 충돌하면 본문이 틀린 것이다.

# 2. Product & UX Contract — 사용자가 받는 결과를 먼저 고정한다

renderer가 없어도 CLI·API·저장·운영자·외부 구현자가 관측하는 동작은 제품 계약이다. 다음을 적는다.

- **목표와 문제**: 무엇이 잘못됐고 완료 후 무엇이 달라지는가.
- **명시 요구 vs 해석**: 사용자 문장과 설계자의 추론을 분리한다.
- **동작 흐름**: 시작 행동/이벤트 → 중간 상태 → 성공/실패 결과.
- **상태와 전이**: loading·empty·error·cancel·retry·close·restart·concurrency 중 실제 관련 상태만.
- **범위/비범위**: 비범위가 범위의 실행을 막지 않는지 확인한다.
- **용어/이름**: 새 이름을 노출하면 기존 의미와 충돌하는지 조사한다.
- **Acceptance Criteria**: 구현 방법이 아니라 관측 가능한 결과를 먼저 쓴다.

사용자에게 다시 물어야 하는 경우: 두 해석이 모두 합리적이고 사용자가 받는 결과가 달라질 때 · 이름·식별자·스키마·공개 계약처럼 미루면 비싸질 때 · 제품 의도·정책·신규 의존성처럼 에이전트가 정할 수 없을 때 · ACTIVE 결정과 새 요청이 충돌하는데 사용자가 변경 의사를 밝히지 않았을 때. 코드 조사로 닫을 수 있는 사실은 묻지 말고 조사한다.

# 3. 요구 비판적 검토

- **증상과 원인**: 요구가 진짜 원인을 겨냥하는가. 권위 신호를 정하고 실측한다.
- **이미 충족됐는가**: 기존 코드로 되는 기능을 다시 만들지 않는다.
- **더 작은 해법**: 구조 변경 없이 목표를 달성할 수 있는지 본다. "제거/정리" 요구는 그 능력 자체가 없어도 되는지 묻는다 — 이동은 제거가 아니다.
- **선행 자료가 맞는가**: 이전 handoff·보고서·가이드의 주장을 코드와 다시 대조한다.
- **기존 결정과 충돌하는가**: docs뿐 아니라 코드 주석·계약 헤더·테스트가 잠근 결정을 찾는다.

이견은 근거와 우려를 적되 작업 회피에 쓰지 않는다. 어떤 가정으로 진행해도 제품 결과가 달라지는 결정만 사용자에게 올린다.

# 4. 조사 게이트

증거 우선순위: 현재 코드·테스트·타입·계약 → 저장소 정본 문서 → 외부 SDK/API는 벤더 1차 문서·실제 패키지 타입/런타임 → 저장소 내부 과거 관찰·주석(보조). 외부 API에서 1차 문서와 내부 관찰이 충돌하면 동일 배포·endpoint·method라는 증거가 없는 한 1차 문서를 기본값으로 둔다.

- 숫자는 승계하지 말고 이번 세션에서 다시 센다. 총계는 내역 합과 검산한다.
- "유일한/항상/절대" 같은 전칭 표현은 `rg`로 반례를 전수 확인한다.
- 대표 샘플만 보지 않는다. 상태 전이·등록·마이그레이션·소비처처럼 빠지면 조용히 깨지는 표면은 전수 grep + N개를 남긴다.
- 기존 테스트를 검증 수단으로 인용하면 그 케이스·핵심 동작이 실제로 있는지 확인한다.
- 문서의 `§표제어`나 "확정 결정"을 인용하면 앵커가 실제로 있는지 grep한다.
- 하위 가이드의 주장을 정본으로 승격할 때는 코드에서 다시 검증한다. 틀렸다면 승계 원본도 고친다.
- 작업 관련 저장소 규칙(eslint boundaries/hooks, 위생 테스트, migration append-only guard, preload/renderer 호출 관례, 디렉토리 `AGENTS.md`)을 설계 입력으로 읽는다. "컴파일된다"와 "이 저장소 규칙에 맞는다"는 다르다.
- INDEX `## 새 handoff 후보` 표에서 이번 작업이 건드리는 파일과 겹치는 행을 읽는다. 그 형태가 이번 코드에 실제로 나타나면 그 후보는 이번 plan의 범위로 들어온다(승격 계기).

# 5. Acceptance Criteria 게이트 — 의미를 검증한다

각 AC에는 `동작 기준 / 검증 수단 / 프로덕션 도달 경로`가 필요하다.

- 부정형("불변/문제 없음/0건")만으로 목적을 표현하지 않는다. 필요한 정상 동작을 쓴다.
- 테스트 파일명을 계약으로 만들지 않는다. 파일을 옮겨도 검증 가능한 행동 단언이 정본이다.
- structural proxy가 semantic 목표를 대신하지 못한다. "함수 1회 호출"·"`Promise.all` 존재"·"시그니처가 X"가 목표를 실제로 보장하는지 적대 사례를 생각한다.
- **장치가 반응하는 방향을 불변식의 방향과 맞춘다.** 불변식이 "X가 있다/쓰인다"면 장치는 X를 지웠을 때 실패해야 한다. 여분의 사본에 반응하는 음성 스윕이나 남은 잔여물에 반응하는 컴파일러 진단은 X가 죽은 코드가 되면 함께 침묵한다(0198 D-010).
- **불변식이 자리까지 말하면** 장치는 X를 지웠을 때뿐 아니라 형제 자리와 맞바꿨을 때도 실패해야 한다. 산출의 존재만 단언하면 자리를 바꾼 회귀는 통과한다(0204 r4).
- **게이트의 완료 조건이 세는 것과 목표가 묻는 것이 다르면** 그 차이를 §10 `실패 의미` 칸에 적는다 — 게이트가 green인 채로 남는 결함이 그 차이만큼이다. 그 칸에 "다른 게이트가 막는다"고 적으려면 막히는 범위를 이 턴에 측정한다(0198 §10).
- `N회`·총량 식을 쓰면 sink를 부르는 프로덕션 호출부를 전수 검색으로 세어 식의 항에 매핑한 뒤 관측 지점을 적는다. 관측 지점이 호출부 일부만 모형하면 단언 범위를 그 주체가 내는 호출로 좁힌다(0194).
- 순서를 요구하면 단계 훅·순서 로그·주입 경계 등 순서를 관측할 방법도 설계한다.
- 사람 실기는 시각·실제 외부환경에만 쓴다. 목록 포함·후보 계산·상태 파생 같은 로직은 순수 테스트로 내린다.
- 선택적 필드는 `true/false/undefined` 의미를 확인한다. 권한·보안은 미지정이 fail-open 되지 않게 한다.
- 외부 SDK로 넘기는 값은 필드 목록이 아니라 SDK가 요구하는 타입/의미를 AC로 잠근다. `as any`/`as never`가 필요한 경계는 별도 계약 테스트 후보다.
- 참조 fixture/example이 구현자를 안내한다면 그것도 계약을 만족해야 한다.

수치·총량·음성 게이트:

- 줄 수·파일 수·모듈 수 같은 구조적 목표는 대상의 단계 지도를 먼저 그리고 달성 가능한 이유를 적는다. 추정이 어려우면 상대 목표를 쓴다.
- 총량 임계는 제거 대상과 허용 대상이 섞이지 않았는지 형태별로 분해한다.
- `rg … = 0` 같은 음성 게이트는 이력·허용 예외를 먼저 열거해 술어에서 뺀다. 음성 게이트는 "없다"만 잠그므로, "있다/쓰인다"가 불변식이면 양성 단언과 짝짓는다.
- AC가 25건을 넘으면 handoff·구현 단위를 나눌 수 있는지 먼저 본다.

# 5-A. V / Trace Matrix — 열거 원문을 만든다

`docs/handoff/AGENTS.md §공통 V 추적 프로토콜`의 vocabulary와 requiredness를 그대로 쓴다.

- 상속할 V가 없으면 필요한 수준으로 Baseline V를 만든다. 기존 handoff의 V를 상속하면 handoff·plan revision·commit을 고정하고(commit은 공유 브랜치에서 `git cat-file -t`로 확인한 해시만 — 아니면 `검증자 기입` 자리표시자), 변경이 시작되는 수준부터 아래쪽과 영향받은 상위 회귀만 Delta V로 적는다.
- Product/UX 결과가 바뀌면 `R↔AT`, end-to-end 상태·수명주기가 바뀌면 `SD↔ST`, production 경계·producer/consumer·이벤트·저장소가 바뀌면 `AR↔IT`, 모듈 불변식·알고리즘·seam이 바뀌면 `MD↔UT`를 포함한다.
- 노드마다 `NEW`·`CHANGED`·`INHERITED`·`SUPERSEDED`와 기준선 출처/대체 노드를 적는다. 영향 없는 기준 V를 복사하지 않고, 명시적으로 비영향을 판정할 inherited pair만 `NOT_REQUIRED`로 적는다. pair의 왼쪽 노드를 `SUPERSEDED`로 나누면 그 pair의 AC와 선택 적대 증거가 어느 대체 pair로 가는지, 아니면 폐기 근거를 적는다(0238).
- 모든 `NEW`·`CHANGED` 왼쪽 노드에 같은 레벨 `REQUIRED` pair를 둔다. 변경 경로가 기존 상위 동작에 닿으면 해당 `INHERITED` 노드를 `REGRESSION`으로 고른다.

pair마다 다음을 둔다. 이것이 verify가 sweep하는 열거 원문이다.

- **production path** `start → edges → end`.
- **§10 자리 목록과 그 자리 검색 명령.** 자리는 §10 항목이 아니라 path의 edge 중 그 계약 값을 운반하는 edge다. 검색 술어는 불변식의 주어로 쓰고(해법 이름 금지, 코드 라벨이면 표본이 참인지 확인), 범위는 pair path가 지나는 소스 전체로 둔다(0194 r4·0209 r11·0262 r5). 이 목록이 구현·검증의 분모다.
- **자리별 직접 oracle 좌표** — 기존 `파일:테스트명` 또는 구현자가 만들 테스트(파일·진입점·구별 입력·관측 대상). 좌표 조건은 `docs/handoff/AGENTS.md §공통 V`를 따른다: 자리가 실행 구간 안이고 양 끝을 mock하지 않으며 production 조립이 주입하는 의존성을 빼지 않고 운반 값을 기본값·형제와 구별되게 준다. typecheck·코드 읽기는 oracle이 아니다.
- **규칙 칸 ↔ UT 입력 칸을 1:1로 맞춘다.** 자리 규칙이 조건에 따라 다른 결과를 적으면 분기마다 그 분기로 가는 입력을 oracle 칸에 적는다. 입력 칸이 규칙 칸보다 좁으면 그 분기는 아무도 잠그지 않는다(0292 · 0294 r3에서 13분기가 입력 없이 남았다).
- **선택적 적대 증거**는 oracle이 구조적 proxy·0건/전수 주장·배선 존재처럼 방향·민감도를 따로 입증해야 할 때만 고른다. 선택 이유와 심을 자리를 적고, 같은 결함이 여러 자리에서 가능하면 자리마다 등록한다.
- **선언 경계** — 이 계약이 일부러 다루지 않는 형태·입력을 §10 `실패 의미`·"게이트가 green인 채로 남는 차이"에 적는다. verify는 그 안의 반례를 `경계`로 처리해 판정에 쓰지 않는다. 미리 적어 두면 확장 창(verify 1·2회째)을 경계 결정만으로 소비하는 일이 줄어든다. 측정하지 않은 보호는 경계로 적지 않는다.

**검사기·게이트·스캐너처럼 열린 입력 집합을 판정하는 산출물**은 열거로 닫히지 않는다(0294 r1~r3에서 같은 축이 세 번 열렸다). 다음 중 하나를 설계에 넣는다.

- 모르는 형태는 red로 막고(fail-closed) 허용 목록에 올려야 통과시킨다 — 놓친 형태가 거짓 통과가 아니라 눈에 보이는 오탐이 된다.
- 판정이 다루는 식 노드 종류(예: TypeScript `SyntaxKind`)와 해석 방식을 표로 고정하고 칸마다 해석/경계/red를 적는다 — "모든 경우"가 컴파일러가 정한 유한 집합이 된다.

보안·데이터 무결성처럼 이번 요구에 필요한 제약은 V node·Decision·AC·§10에 귀속시킨다. 수정 subtree gate와 repository/message-bus 검사는 현재 변경 산출물의 운영 완료 조건으로 따로 열거하며 새 제품 범위를 만들지 않는다.

READY 전 V mode·상속 기준, 필요한 레벨, `NEW`·`CHANGED` node의 pair, 영향받은 상위 회귀, `SUPERSEDED` pair 증거의 이관, 자리 검색 명령으로 고정한 분모와 자리별 좌표, 규칙 칸↔입력 칸 대응, 선택 적대 증거의 이유와 자리, 선언 경계, 적용 gate를 확인한다. 하나라도 없으면 READY가 아니다.

# 6. Technical Design — 구현자가 바로 작업할 수 있게 쓴다

Product/UX Contract가 무엇을 정했다면 여기서는 어떻게를 정한다. 현재 흐름과 변경 후 흐름(필요하면 ASCII) · 레이어·모듈별 책임과 import 방향 · 변경/신규 타입·함수·포트·IPC/API 계약 · producer → 정규화/상태 → consumer 경로 · lifecycle/cleanup/cancel/retry/error propagation · 저장·마이그레이션·하위 호환 · 테스트 seam과 종류 · 변경 파일과 역할을 적는다.

구현 가능성 방어선:

- electron/DB/native 의존 모듈의 순수부를 테스트하려면 같은 파일 함수가 아니라 import graph가 끊긴 별도 파일 seam까지 지정한다.
- 정책 파라미터는 단위·범위·의미를 계약·시그니처 수준에서 고정한다. 배타적 상태는 flat flags보다 discriminated union을 우선한다.
- "같은 규칙"을 여러 레이어가 쓰면 SSOT 위치와 강제 방법을 지정한다. 복붙 정규식은 금지한다.
- 참조 구현·fixture·다른 브랜치를 설계 입력으로 쓰면 계약의 union/enum 멤버를 전수 나열하고 각각을 다루는지 표시한다.
- 기존 메커니즘을 재사용한다고 쓸 때 새 대상이 요구 형상과 적용 시점을 만족하는지 확인한다.
- 계약 제약 필드는 누가·언제 강제하는지 적는다. 지점이 여럿이면 전부 나열한다 — 하나만 적으면 구현도 하나만 닫는다.
- 한 동작이 저장소를 둘 이상 쓰면 먼저 그 사실을 적는다. 원자적으로 함께 쓸 수 없는 저장소를 순서대로 쓰면 쓰기 지점마다 실패 시 관측 상태를 적고, 허용할 수 없는 조합은 설계로 없앤다(순서 교체·포인터 교체·2단 쓰기). 산출물이 문서인 작업도 같다 — 같은 판정이 산출 문서와 `INDEX.md` 보드 두 곳에 살면 §10에 사본 전부를 지점으로 적는다.
- 부팅·초기화에서 레지스트리·스토어 값을 새로 늘리면 기존 소비처를 전수 나열하고 영향을 확인한다.
- 로그·경고·중복 오류 같은 증상을 없앨 때 그 증상이 가리던 실제 상태 변화가 남는지 확인한다.
- 표시 계약은 producer 기준과 consumer 파생 규칙을 쌍으로 설계한다. 파생 가능한 합성값으로 소비자가 정본을 우회하지 않게 한다.
- 모델 컨텍스트·네트워크 요청·배치를 늘리면 원천 상한 × 배치 상한으로 worst-case를 계산한다.
- 캐시·snapshot·hoisting·호출 축소는 "덜 하면서 잃는 부수 효과"를 적고 회귀 테스트로 만든다.

배포·플러그인·외부 구현자가 구현할 port/schema/config를 만들거나 바꾸면 그 계약 문서가 실제 진입 경로다. AC에 shape(문서 예제가 실제 타입에 대입되어 typecheck되는가)와 semantics(성공/실패/null/재시도 의미가 contract test와 맞는가)를 모두 둔다. 시그니처가 같아도 구현자의 행동이 달라지는 의미 변경이면 문서를 같이 고친다.

# 7. 문서 정합성 게이트

본문을 다 쓴 뒤 한다.

1. Decision Ledger의 모든 `ACTIVE` 항목이 Product/UX·AC·Technical Design에서 유지되는지 확인한다. AC가 ACTIVE Decision의 반대를 요구하면 문서 결함이다.
2. 같은 대상(수명주기·식별자·상태·연결 수·오류 의미)을 여러 절이 서술하면 나란히 읽어 충돌을 찾는다.
3. Product/UX의 각 핵심 동작이 Technical Design의 경로와 AC에 연결되는지 추적한다.
4. V mode·상속 기준이 맞고 모든 `NEW`·`CHANGED`·영향받은 `INHERITED` node가 requiredness에 맞는 pair·§10·증거를 갖는지 확인한다.
5. 기존 결정·규칙 표는 본문을 훑은 뒤 실제 본문 문장 기준으로 마지막에 채운다.
6. 인용 경로·문서 앵커·기존 테스트 케이스가 실제로 있는지 확인한다.
7. 범위/비범위가 사람 실기나 프로덕션 도달 경로를 스스로 막지 않는지 확인한다.

교차검증 결과는 관측으로 남긴다. 체크박스 `[x]`는 검사를 했다는 증거가 아니다(0190: 전 항목 `[x]`인 채 plan 결함 3건이 구현까지 갔다). 1의 결과는 Ledger 갱신 메모에 `ACTIVE 결정 ↔ AC 대조: 충돌 0` 또는 `D-00N ↔ ACn (판정)` 한 줄로 적고, 2·4·6은 대조한 문장·pair·경로를 인용한다.

# 문서 문장 규칙

[`docs/handoff/AGENTS.md §산출물 문장 규칙`](../../../docs/handoff/AGENTS.md)을 따른다 — 판정 먼저, 주장 한 줄에 관측 하나, 표 한 칸 3줄, 문단 3문장. plan에서 특히:

- Part I과 Part II에 같은 사실을 두 번 쓰지 않는다. Part I은 관측 결과, Part II는 경로·계약이다.
- 조사 결과는 서술이 아니라 `대상 / 검색 / N / 의미` 표로 적는다.
- 줄이는 대상은 서술이다. AC·강제 지점·전수 개수·재현 수단은 줄이지 않는다.
- 사용자 문장의 이유·조건절은 요약하지 않고 원문으로 인용한다 — 조건절이 대안을 지정하는 경우가 있다(0183).

## verify 뒤 plan 갱신 — 창 안과 창 밖

미해결 항목은 `[검증자 기입] 파생 이슈`에 누적한다. Product/UX Contract·Decision Ledger·영향받지 않은 상위 V node를 매번 다시 쓰지 않는다.

- **FAIL**(이행 결함·현재 결함)은 기존 pair에 귀속한 파생 이슈로 좁혀 재구현한다. plan은 바뀌지 않는다.
- **PLAN_GAP은 재구현 전에 여기서 닫는다.** 필요한 Decision·AC·V node/pair·경로·§10·oracle을 새 Delta V revision으로 정정하고, 구 행을 덮어쓰지 않고 supersede한다. `RETURN_TO_PLAN`을 구현자에게 그대로 넘기지 않는다.
  - plan 내부 불일치·목록 미고정(이행): 언제든 정정한다. §10 자리 목록의 gap이면 지적된 자리만 더하지 않고 그 pair 목록을 자리 검색 명령으로 다시 열거해 한 번에 고정한다 — 한 자리씩 더하면 다음 검증이 다음 자리를 연다.
  - 현재 결함의 계약 정정: 언제든 한다.
  - **확장 후보(verify 1·2회째 뒤에만)**: 항목마다 채택하거나 경계로 선언한다. 채택이면 열거 원문(AC·§10·규칙 칸·UT 입력 칸)에 넣어 이후 이행 의무로 만든다. 경계면 1줄 근거를 적는다 — 검사기 산출물이면 "트리에 같은 형태 0"을 실측해 함께 적는다(트리에 있으면 경계가 아니라 현재 결함이다). 채택은 창 안에서 끝낼 수 있게 한 번에 한다.
  - 경계 선언만 있고 새 의무가 0인 ΔV는 구현 턴 없이 verify로 보낼 수 있다(INDEX에 "규범 변경만 — 구현 없음").
- **plan 동결**: verify 2회째 뒤의 설계 턴이 열거 원문을 늘릴 수 있는 마지막 턴이다. 그 뒤 새 열거 항목에는 출처(현재 결함 · plan 내부 정합 · 사용자 결정)를 적는다. 창 밖의 확장 후보는 채택하지 않는다 — 후보 표에 남는다.
- 설계 계약이 틀렸다는 증거가 생기면 관련 Decision/AC/Technical Design만 고치고 이유를 남긴다. 고쳐 쓴 AC 행은 §5 AC 게이트와 READY self-review의 AC 항목을 다시 통과시킨다 — 정정이 게이트를 안 받으면 틀린 기준으로 채점하게 된다(0194 AC18).
- 사용자 결정 변경이면 기존 Decision을 `SUPERSEDED` 처리한다. 실패로 위장하지 않는다. 사용자 요구 변경으로 plan을 다시 쓰는 것은 같은 라운드 안의 턴이고, 그 ΔV의 NEW·CHANGED 노드는 다음 verify 2회 동안 그 범위에서만 확장 창이 다시 열린다.
- 반복 라운드에서 같은 종류가 다시 나오면 `handoff-review` 신호로 올린다. failure-patterns를 직접 갱신하지 않는다.

## 마무리

`docs/handoff/INDEX.md`를 `plan/READY`와 다음 주체로 갱신하고 커밋 형식은 `docs/git-template.md`를 따른다. 대상 커밋 칸과 plan 메타에는 공유 브랜치에서 `git cat-file -t`로 확인한 해시만 적고, 확인할 수 없으면 `(… — 검증자 기입)` 자리표시자를 남긴다(`docs/handoff/AGENTS.md §INDEX.md 운영`).

plan의 규범 행을 바꾸는 커밋은 구현 산출과 같은 커밋에 담지 않는다 — Decision·AC·V node/pair·§10 강제 지점이 규범 행이고, `plan/READY` 커밋도 verify/FAIL·RETURN_TO_PLAN 후 정정도 같다. 설계자와 구현자가 같은 에이전트여도 마찬가지다. verify §0의 기준선 잠금은 "구현 전 plan"을 diff로 꺼낼 수 있을 때만 작동한다(0189 r1·0194 r3).
