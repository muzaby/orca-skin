# docs/ — 코딩 에이전트용 가이드

이 디렉토리는 **제품 정의 · 구현 사양 · 현재 아키텍처 · 결정 근거 · 운영 절차**를 담는다.

> **어느 문서를 열지는 [`INDEX.md`](INDEX.md) 가 안내한다.** 본 문서는 *문서를 쓰고 고칠 때의
> 규칙*만 담는다 — 인벤토리를 여기 두면 문서가 늘 때마다 두 곳을 고쳐야 하고, 곧 갈라진다.

## 문서를 어디에 두는가

| 성격 | 위치 | 경계 |
|---|---|---|
| 시스템이 **어떻게 구성돼 있는가** | `arch/{backend,frontend}/` | *서술* — 현재 상태만 |
| 사람이 **무엇을 어떤 순서로 하는가** | `guides/` | *지시* — "~한다" 로 쓴다 |
| **왜 그렇게 결정했나** | `decisions/` (ADR) | 문제 → 선택지 → 선택 → 포기한 것 → invariant |
| 무엇을 만들지 / 어떤 기술로 | `PRD.md` / `TRD.md` | — |
| 채널 계약 · 용어 | `IPC_CONTRACT.md` · `GLOSSARY.md` | SSOT — 다른 문서는 인용만 |
| 전략 논거 · 외부 사례 연구 | `etc/` | evidence — 현재 규칙 아님 |
| 외부 공식 문서 원문 | `spec/<vendor>/` | **편집 금지**, 통째로 덮어쓰기만 |
| 완료된 페이즈·핸드오프 이력 | `archive/` | 과거 사실 — 현재 규칙 아님 |
| 코드를 세어 만든 수치 | `generated/` | **생성물** — 사람이 편집하지 않는다 |

- **한 주제가 `arch/` 와 `guides/` 둘 다면 사실은 `arch/` 에 두고 `guides/` 는 링크한다.**
  사실을 양쪽에 적으면 반드시 갈라진다.
- 어디에 속할지 모호하면 `docs/` 최상위를 기본값으로.

## 작성 규칙

1. **한국어, 표 위주, 결정 사항 중심.** 기존 톤을 유지한다.
2. **코드에서 셀 수 있는 수치를 쓰지 않는다.** 채널·도메인·슬라이스·contracts·settings 키·
   마이그레이션·핸들러·variant 개수는 [`generated/inventory.md`](generated/inventory.md) 가 갖는다.
   본문에는 **정본 코드 경로**를 적고 그 문서를 링크한다.
   `app/scripts/check-doc-inventory.mjs` 가 CI 에서 강제한다 — 어기면 빌드가 깨진다.
   > 이 규칙은 관례로 두면 지켜지지 않는다는 것이 관측됐다. 0177 이 전수 동기화한 채널 수가
   > 6일 만에 다시 두 갈래로 갈라졌고, 같은 규칙을 산문으로 적어둔 문서 하나에서만 지켜졌다.
3. **사실을 복제하지 말고 링크한다.** 같은 사실이 두 문서에 있으면 하나를 SSOT 로 정하고
   나머지는 인용한다.
4. **`arch/` 에 이력을 쓰지 않는다.** `0180에서 제거` · `77 → 76` · `직전 0177…` 같은 델타
   서술은 architecture 가 아니라 changelog 다. *현재 어떻게 동작하는가*만 쓰고, 이유는
   `decisions/` 의 ADR 로 링크한다(`Decision rationale: ADR-00N`). 핸드오프 번호는
   **출처 표기**(`(0087~0089)`)로만 쓴다.
5. **문서를 추가하면 [`INDEX.md`](INDEX.md) 라우팅 표를 갱신한다.** 표에 없으면 에이전트가 찾지 못한다.
6. **IPC 채널을 바꾸면 `IPC_CONTRACT.md` 를 같은 PR 에서 갱신한다** (변경 절차는 §6).
7. **외부 공식 문서 미러는 2단**이다. (a) *원문 미러* `spec/<vendor>/` — 편집 금지, 덮어쓰기로만
   갱신. (b) *해설 미러* `<vendor>-*-spec.md` — Orca 채택 표기·정리표·안정된 절 번호.
   외부 사실(플래그·이벤트 스키마)은 항상 원문 미러를 따른다.

## 코드와 문서가 어긋날 때

즉시 사용자에게 묻지 말고 먼저 무엇이 어긋났는지 가른다.

| 상황 | 처리 |
|---|---|
| 문서가 낡았다 (코드가 명백히 옳다) | 에이전트가 조사 후 문서를 고친다 |
| 코드가 계약을 위반했다 (명백한 버그) | 에이전트가 조사 후 코드를 고친다 |
| 진행 중 작업 때문에 일시적으로 다르다 | `handoff/INDEX.md` 확인 후 그대로 둔다 |
| **제품 동작·공개 계약·데이터 포맷·되돌리기 어려운 결정** | **사용자에게 묻는다** |
| **유효한 두 설계 중 하나를 골라야 한다** | **사용자에게 묻는다** |

**PRD §11 / TRD §15 의 Open Questions 는 단독 결정 금지** — 사용자에게 묻는다.

문서에 명시된 **채택 결정**(예: "Provider 어휘 폐기, Backend/Adapter 로 통일" — GLOSSARY §3,
"2계층 영속성 모델" — `arch/backend/persistence.md`)은 협의 결과다. 바꾸려면 먼저 확인한다.
