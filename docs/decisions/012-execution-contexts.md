# ADR-012 — 실행과 상태를 셸 밖 두 호스트로 나눈다

- 상태: 채택
- 설계 기록: [handoff 0324](../handoff/0324-execution-contexts-ui-responsiveness/plan.md)
- 현재 구조: [`arch/execution-model.md`](../arch/execution-model.md)

## 맥락

모든 일이 Electron main 한 프로세스에서 돌았다. 동기 DB 호출·세션 본문 조회·하네스 준비가 main 의 이벤트
루프를 잡으면 창 이동·크기 조절·입력이 함께 멈췄다. renderer 에서는 구문 강조와 큰 diff 계산이 같은
문제를 만들었다.

## 결정

1. main 은 **셸**만 맡는다 — 창·트레이·업데이트, 두 호스트의 감독, Electron 권한 작업(셸 서비스).
2. **실행**(어댑터·SDK·세션 런타임·git·셸 프로세스)은 에이전트 호스트, **상태**(DB·설정·비밀·인증·턴
   저장)는 데이터 호스트가 맡는다. 둘 다 `utilityProcess` 다.
3. 창은 채널을 소유한 호스트와 **포트로 직접** 말한다. 채널마다 소유 프로세스는 하나이고 타입으로 고정한다.
4. 턴 이벤트는 저장과 표시에 **함께** 보낸다. 화면은 저장을 기다리지 않고, 저장 실패는 그 턴을 오류로 끝낸다.
5. 턴 이벤트에 순번을 두지 않는다. 대신 "턴은 시작한 창의 문서와 수명을 같이한다"와 "진행 중인 캐시
   세션에는 로드 결과를 적용하지 않는다"를 계약으로 둔다.
6. 세션 본문은 조각으로 보내고 한 번에 반영한다.
7. renderer 의 구문 강조·diff 계산은 계산 워커로 보낸다.
8. 프로세스 사이의 import 경계와 "경로를 건너뛴 직접 호출"은 가드가 막는다.

## 근거

- 실행과 상태를 한 호스트에 두면 동기 DB 호출이 턴 중계와 같은 이벤트 루프를 쓴다. 나누면 느린 조회가
  화면 중계를 늦추지 않는다.
- DB 를 여는 프로세스가 하나면 쓰기 순서와 복구 책임이 한 곳에 있다.
- 하네스가 죽거나 멈춰도 과거 대화·설정·인증은 데이터 호스트가 계속 답한다.
- 순번과 "붙기"(스냅샷과 실시간 이음)는 창이 하나이고 턴이 창의 문서보다 오래 살지 않는 동안 필요한
  경로가 없다. 그 전제를 계약과 테스트로 잠그는 편이 프로토콜을 늘리는 것보다 작다.

## 결과

- 실행 쪽 코드의 DB·설정 접근은 요청이 되어 언제나 비동기다.
- 설정 사본은 패치 통지가 닿기 전까지 옛 값이다.
- 비밀은 데이터 호스트가 기동 때 풀어 메모리에 둔다.
- 데이터 호스트가 죽으면 진행 중 턴은 오류로 끝난다. 다시 보내기는 사용자가 한다.
- 창을 둘 이상 만들거나 창이 닫혀도 턴이 계속 돌게 하려면 결정 5 를 먼저 다시 설계한다.
- 본 화면은 두 호스트가 모두 준비된 뒤에 뜬다. 데이터 호스트만 준비되면 띄우는 안은 후속 후보다.
