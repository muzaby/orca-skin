## 구현 조건과 남긴 곳

- **읽기·ID 공급원.** `localMessages` 의 keyed/legacy, `projectNativeHistory` 의 native/alias, frontier 양쪽, 마지막 target, 0과 부재, 첫·작은 소유자, 고아/로컬 tail, DTO 펼침은 N의 값·순서·유일성으로 대조했다. 보관본의 archive 분기는 A의 실제 DB 경로에서 따로 다루었다. i계열 최신 기계 조사에서 추출한 AST 문법 역할은 24개였고 네 마지막 역할의 직접 치환은 r3.4에서 모두 red였다. AST 범위 숫자는 의미 분기의 분모로 쓰지 않았다.
- **식별 경로.** `appendAssistantPart`에서 키의 유무 → owner 유무와 역할 → 부분 이력·소유 표식 → merge key와 part slot 순서로 분기를 확인했다. `APPEND_COMMITTED_USER_MESSAGE`의 명시 키/clientId/생성 키, 중복 조기 반환, 낙관 후보 역할과 개수, 단 한 번의 정본 배치, store의 pending 정리는 r6/r7/r12에 걸친다. 키가 이미 있는 행의 객체 보존을 별도 단언했다. 사용자 입력의 첨부/요구사항 payload 포맷, LOAD_SESSION의 provider 및 작업공간 UI 기본값은 이 규칙의 분기가 아니다.
- **보류 소유권.** 성공/오류 결과에서 산출물의 부재/존재, 명시 owner/도구 인덱스, 도구/응답/없는 owner, 부분/완전 이력, 같은 publication의 중복과 도착 순서, 양쪽 assistant 이웃과 user 경계를 구분했다. `holdPart`의 최초 수신과 같은 키 재전송, `mergeHeldParts`의 메시지별 patch와 동봉된 출력의 교차, `finishHeldParts`의 두 보류표 및 0건 진단을 각각 별도 입력에서 관찰했다.
- **페이지.** `PREPEND_HISTORY`는 페이지 안 첫 중복 제거 → 기존 prefix와 overlap 순번 비교 → 나머지 page가 비면 기록 생략 → seam이 정상/비정상이면 prepend/reset → 보류 병합 → reachedStart 종료의 순서로 대조했다. 기존과 새 접두 4개 기호 및 두 역할의 조합을 직접 계산했다. store의 존재하는 비활성 key, 없는 key, 활성 key를 잘못 만드는 두 위치를 구별했다. 불완전에서 완전으로 전환할 때 `finishHeldParts`가 양쪽 맵을 비우고, 이후에는 부분 이력에서만 hold한다. 따라서 `historyComplete === true`인 정상 상태에 비어 있지 않은 보류표를 넣고 그 일관성 검사 피연산자를 따로 강제하는 입력은 만들지 않았다.
- **분모 제한.** `Message.id`가 없는 과거 보관본은 reader가 renderer로 보내기 전에 ID를 부여한다(i6). 테스트 전용으로 타입 계약을 깨서 구성한 임의 상태, 알 수 없는 SQL 조작, 복수 페이지에 분산된 모든 순열을 41개 규칙에 덧붙이지 않았다. completion/error의 일반 metadata 전달·전체 패널 갱신·parts별 렌더·글자 높이 보정은 각각 해당 규칙/경로의 증거를 사용한다.
