기준은 `c7d2adf2`, 적용 소스는 이 문서를 담은 r1.3 구현이다. Electron 39.8.10과 Xorg에서 같은 제품 컴포넌트와 진단 입력을 사용했다. R-H는 기준 빌드의 같은 상호작용에서 호스트 시간 T1+T2와 창 시간 T3+T4+T5의 중앙값을 비교한다. R-W는 합류 레인의 이미지 작업 p95, R-R은 최대 입력의 long task와 동기 작업을 사용한다. T5는 두 번째 프레임까지의 상한이다.

**표본 해석.** 자원·패널·사용량 및 일곱 호스트 조회는 예열 1회 후 9회다. 9개에서 nearest-rank p95는 최대와 같다. 자원 목록의 두 프레임 상한 중앙/최대는 1,203.1/1,604.7→6.3/20.8ms다. 패널 표본의 `longTasks`·`frameGapsMs`는 한 번의 댓글과 폼 조작 전체를 담는다. 기준에서 160ms 이상 task 76건, 적용에서 30건이었다. 공급자와 차트의 일부 프레임은 여전히 160ms를 넘었다. 테스트도 실행되던 Linux 머신에서 측정했고 실제 장비의 프레임 판정은 0330으로 넘긴다.

**구간과 미측정.** 호스트 표본의 T1은 핸들러 구간, T2는 왕복 잔여, T3·T4는 창 가공·commit, T5는 프레임 상한, C1은 직렬화 바이트, C2는 마운트 행이다. visible 워커 요청이 없는 조회에서 T6은 해당 없음이다. 차트 `dataMs`는 실제 DB 집계, `roundTripMs`는 창 왕복, `deriveMs`는 같은 자료의 일·주 파생, `firstCommitMs`는 첫 UI commit, `paintMs`는 차트 표시 확인 뒤 두 프레임이다. 자원·패널의 `commitMs`에는 동기 React 렌더가 함께 들어간다. 별도 계측하지 않은 필드, 한 번의 기능 재생에서의 백분위, 합성 이벤트로부터의 OS IME 성능은 판정 불가로 둔다. 포트 크기나 프레임 대기를 동기 처리 시간으로 더하지 않는다.

**재생.** 앱 의존성을 설치한 `app` 디렉터리와 활성 X 디스플레이에서 `node scripts/measure-stage-d.mjs`에 `--resources`, `--panel-timings`, `--usage`, `--data-flows`, `--interactions`, `--geometry`, `--overlap`, `--installer`, `--host`, `--shell` 중 하나를 붙인다. 기준 재생은 별도 `c7d2adf2` checkout에 구현 커밋의 `app/scripts/measure-stage-d.mjs`와 `app/scripts/stage-d{,-baseline,-host}` 진단 소스만 복사하고 비교할 모드에 `--baseline`을 붙인다. data host에는 Electron용 better-sqlite3, Vitest와 호스트 번들 smoke에는 Node용 네이티브 모듈을 쓴다. 셸의 최소·최대화 시험은 창 관리자가 있는 디스플레이에서 실행한다.
