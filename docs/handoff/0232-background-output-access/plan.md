# Part I — Product & UX Contract

## 1. Context / 목표

- 해결하려는 문제: 백그라운드 작업이 끝나도 화면에 남는 것은 **알림 요약 한 줄**뿐이다. SDK 가
  `task_notification.output_file` 로 가리키는 전체 출력에 도달할 경로가 없다.
- 완료 후 달라지는 것: 작업 상세에서 전체 출력을 열 수 있고, 실행 중 부분 출력과 완료 시점
  스냅샷과 이후 파일 변경이 서로 구분된다.
- 성공을 사용자 관점에서 한 문장으로: vitest 가 끝난 뒤 실패한 테스트 목록을 앱 안에서 읽을 수
  있다.

## 4. 요구 비판적 검토

| 질문 | 판단 | 근거 |
|---|---|---|
| 요구가 원인을 겨냥하는가 | 타당 | `rg output_file app/src` → 0건. 읽을 경로가 아예 없다 |
| 이미 기존 코드가 충족하는가 | 아니오 | 다만 **기존 파일 읽기 가드가 있다** — `adapters/workspace-guard.ts` 의 `resolveGuardRoots` 가 편집 미리보기(0229)에서 같은 문제를 이미 풀었다. 재사용 후보다 |
| 더 작은 해법이 있는가 | 있다 | 1단계는 "경로를 보여주고 탐색기로 열기" 다. 읽기·렌더링 없이 도달성만 준다. D-204·D-205 가 닫히기 전 대안 |
| 선행 자료의 주장을 코드와 대조했는가 | 예 | `claude-taskxxx-spec.md:159` 가 `output_file` ❌ — 코드와 일치 |
| ACTIVE 결정과 충돌하는가 | 주의 | 0223(artifact publisher)이 이미 산출물 파일 카드·경로 검증을 갖는다. **그 메커니즘을 재사용할지 먼저 본다** — 두 번째 파일 뷰어를 만들지 않는다 |

- **사용자에게 올릴 결정**: D-204(읽기 허용 범위) · D-205(대용량 정책) · 1단계 축소안 채택 여부.

## 5. 동작 / 사용자 흐름 (초안)

```text
[작업 상세를 연다]
  → 요약(알림) + "전체 출력" 진입점
  → 열기
      → 접근 가능        → 부분 표시(뒤에서부터 N KB) + 더 보기
      → 아직 없음        → "아직 생성되지 않음"
      → 권한 없음/삭제됨 → 사유별 문구, 완료 카드는 유지
      → 원격 경로        → 읽지 않고 경로만 표시
  ↘ 완료 후 파일이 바뀜 → "완료 시점 스냅샷과 현재 파일이 다르다" 표시
```

### 상태와 전이

| 시작 상태/이벤트 | 시스템 동작 | 사용자에게 보이는 결과 |
|---|---|---|
| `task_notification.output_file` 수신 | 작업 레코드에 출처·경로 보존 | 상세에 "전체 출력" 진입점 |
| 실행 중 파일이 계속 자란다 | 부분 읽기 | "부분 출력" 라벨 — EOF 를 완료로 읽지 않는다 |
| `canReadOutputFile: false` | 읽기 시도 안 함 | 경로만 표시 |
| MCP `resource_links` 수신 | `tool_use_id` 로 원래 호출에 연결 | 결과 파일 카드 1개(중복 없음) |

## 6. 범위 / 비범위

- **범위**: F-08 `output_file` 보존·읽기·표시 · F-09 `resource_links`/`resourceLinks` 연결 ·
  F-10 읽기 안전성(경로 검증·대용량·쓰는 중 파일·완료 스냅샷과 현재 파일 구분).
- **비범위**: 출력 본문을 모델에게 되돌리는 경로(명시적 사용자 입력 동작으로 별도) · 원격 URI
  다운로드 · 0223 산출물 게시 흐름 변경.

| 미룬 항목 | 나중에 하면 더 비싼가 | 처리 |
|---|---|---|
| 출력 참조의 저장 형태(원래 필드명·출처·접근 상태) | **예 — 영속 데이터 포맷** | 이 handoff 에서 확정 |
| 본문을 모델에 재투입 | 아니오 | 후속 |

## 7. Requirements / Acceptance (초안)

| R | AT | 동작 기준 |
|---|---|---|
| R-201 | AT-201 | `output_file` 이 작업 레코드에 원래 필드명·출처와 함께 보존된다 |
| R-202 | AT-202 | 파일이 없거나 권한이 없어도 **종료 상태 카드가 사라지지 않는다** |
| R-203 | AT-203 | 실행 중 읽기는 "부분 출력" 으로 표시되고 EOF 가 완료로 해석되지 않는다 |
| R-204 | AT-204 | 허용 범위 밖 경로는 읽지 않는다 — 정규화·심볼릭 링크·Windows 경로 경계 |
| R-205 | AT-205 | 완료 시점 스냅샷과 현재 파일이 다르면 그 사실이 표시된다 |
| R-206 | AT-206 | `resource_links` 가 `tool_use_id` 로 원래 호출에 연결되고 카드가 중복되지 않는다 |
| R-207 | AT-207 | 호스트 읽기가 transcript 에 도구 호출로 기록되지 않는다 (D-202 음성 단언) |

> AT-204 는 **사람 실기로 미루지 않는다** — 경로 정규화는 순수 로직이다. Windows 경로 경계는
> fixture 로 단언하고, 실제 드라이브 동작만 실기로 남긴다.

# Part II — Technical Design (방향)

## 8. Research — 이미 확인한 것

| 발견 / 제약 | 근거 |
|---|---|
| `output_file` 판독 0건 | `rg output_file app/src` |
| `resource_links`·`resourceLinks` 판독 0건 | `rg resource_links\|resourceLinks app/src` |
| workspace 가드 루트 해석기가 이미 있다 | `app/src/main/adapters/workspace-guard.ts` `resolveGuardRoots` |
| 편집 미리보기가 그 가드 안에서 파일을 읽는 선례 | `claude.ts:390-394` (0229) |
| 산출물 파일 카드·경로 소유 메커니즘이 이미 있다 | 0223 artifact publisher |

### 남은 조사

| 대상 | 방법 | 왜 필요한가 |
|---|---|---|
| `output_file` 의 실제 경로 형태(절대/상대, 임시 디렉터리) | 실제 로그 | D-204 의 허용 범위가 그것에 달렸다 |
| 0223 의 파일 카드를 재사용할 수 있는가 | 코드 대조 | 두 번째 뷰어를 만들지 않기 위해 |
| `canReadOutputFile` 가 SDK `0.3.220` 선언에 있는가 | 배포물 `.d.ts` | 없으면 D-203 이 도달하지 않는다 |

## 9~15

D-204·D-205 확정 후 작성한다. 고정된 설계 제약:

| 제약 | 이유 |
|---|---|
| 읽기는 main 의 IPC 핸들러 하나가 소유한다 | D-201 · 경로 검증 지점을 하나로 |
| 경로 검증 술어는 `workspace-guard` 와 **같은 SSOT** 를 쓴다 | 복붙 정규식 금지 |
| 반환은 범위 지정 읽기(offset·length)다. 전체 파일 반복 읽기를 만들지 않는다 | 스펙 §2 대용량 요구 |
| 완료 스냅샷의 해시·크기를 저장한 경우에만 "변경됨" 을 주장한다 | 스펙 §2 — 근거 없는 변경 표시 금지 |
