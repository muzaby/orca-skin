# Part I — Product & UX Contract

## 1. Context / 목표

0188(`auth-harness-plugin-lightweight`)은 impl 라운드 10회 후 `verify/PASS` 로 종료됐다. 그런데 그
verify 는 **자기 검증**이었다 — 설계·구현·검증이 모두 Claude Code 였고 `verify.md` 스스로 그것을
판정의 한계로 적었다.

사용자가 네 축의 재검토를 요구했다: 제안서 충실도 · 성능 회귀 · UI/UX 회귀 · 경량화 달성.

완료 후 달라지는 것: **0188 의 실제 결과가 판정 가능한 문서로 남는다.** 시정 여부는 그 문서를
읽은 뒤 별도 핸드오프로 결정한다.

## [구현자 기입] 구현 중 진단 (§3)

이 핸드오프는 **문서만 만든다** — 저장소 쓰기·조기 반환·캐시·동시성·부분 실패가 전부 없다.
§3 의 질문 중 해당하는 것은 하나뿐이다.

- **이 산출물의 유일한 실패 모드는 인용 정확성이다.** 독자가 `파일:줄` 을 열었는데 다른 것이
  있으면 보고서 전체의 신뢰가 무너진다. 초안에서 실제로 4건이 어긋났고(위 #1) 그래서 AC2 를
  "파일 존재가 아니라 **줄 내용**을 본다" 로 좁혔다.
- **두 번째 실패 모드는 채점 층 부족**이었다 — 1층으로만 채점해 정당한 Decision(D-030·D-026)과
  0188 이전부터 있던 상태를 이탈로 오판했다. D-008 이 그 자리를 닫았다.

### r2 에서 새로 보인 것 — "이 산출물은 저장소에 두 번 쓴다"

§3 의 첫 질문("이 동작이 저장소를 몇 곳에 쓰는가")은 코드에만 해당한다고 읽었는데, **문서 산출물에도
그대로 성립한다**는 것이 이번 FAIL 로 드러났다. 이 감사는 결론을 **`audit.md` 와 INDEX 비고 두 곳**에
쓰고, 그 둘은 원자적으로 함께 갱신되지 않는다. r2 개정이 앞의 것만 고치고 뒤의 것을 두자 —

- 두 사본이 **서로 다른 판정**을 말하게 됐다(U2 를 한쪽은 "승인됨", 다른 쪽은 "비범위 침범").
- 그런데 **게이트는 이것을 볼 수 없다.** `check-doc-inventory` 는 링크와 인벤토리 수치만 보고, 두
  산문이 같은 말을 하는지는 검사하지 않는다. r1 이 초록으로 통과한 이유다.
- 독자가 먼저 읽는 것은 **뒤에 있는 사본**이다(§5 흐름의 첫 칸이 보드).

그래서 이번 라운드는 이것을 §10 의 강제 지점으로 올렸다(#8). 코드였다면 "파일 + 키체인을 순서대로
쓰고 사이에서 죽었을 때 무엇이 관측되는가" 라고 불렀을 형태이고, 여기서 관측되는 것은 **철회된 판정**
이다.
