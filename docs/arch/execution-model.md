# 실행 모델 — 누가 무슨 일을 하는가

Orcinus orca 는 한 프로세스가 아니다. 창이 멈추지 않도록 **실행**(하네스·SDK)과 **상태**(DB·설정)를 셸
밖의 두 호스트로 나누고, 무거운 계산은 창의 워커로 보낸다. 이 문서는 실행 주체마다 맡는 일과 맡지
않는 일, 그리고 **어떤 일을 누구에게 어떤 경로로 부탁하는가**를 정한다. 결정의 이유는
[ADR-012](../decisions/012-execution-contexts.md)에 있다.

> 경로를 건너뛴 직접 호출은 가드 `app/scripts/check-ui-thread.mjs` 가 막는다. 규칙 표의 정본은
> `app/scripts/ui-thread-rules.mjs` 이고, 아래 경로 표의 규칙 id 와 가드의 규칙 id 는 같아야 한다
> (가드가 이 문서를 읽어 대조한다).

## 실행 주체

| 실행 주체 | 종류 | 수명 | 맡는다 | 맡지 않는다 |
|---|---|---|---|---|
| 셸 | Electron main | 앱과 같다 | 창·트레이·`app://`·자동 업데이트 · 두 호스트의 감독(기동·포트 중개·종료·재기동·고아 정리) · 셸 서비스(비밀 봉인·해제·대화상자·외부 열기·알림·파티션 세션) · 셸 상태 파일 · 수명 상태 | 턴·세션·DB·설정 파일·업무 핸들러 |
| 데이터 호스트(상태) | `utilityProcess` | 앱 시작 때 뜨고, 죽으면 바로 다시 뜬다 | DB 단독(연결·마이그레이션·복구) · 설정·비밀·인증 파일 · 인증·게이트·사용량·플러그인·예약 작업 · 턴 저장 · 세션 본문 조각 전송 · 데이터 채널 핸들러 · 오류 보고 모음 | SDK·하네스·git·셸 프로세스 기동 |
| 에이전트 호스트(실행) | `utilityProcess` | 데이터 호스트 다음에 뜨고, 죽으면 다음 요청에서 다시 뜬다 | 어댑터·SDK · 세션 런타임 · 턴 정규화·버스·창 중계 · 제목 생성 · git·셸 도구 프로세스 · 확장 배포 · 에이전트 채널 핸들러 | 앱 DB 연결 · 설정·비밀·인증 파일 |
| renderer | Chromium renderer | 창과 같다 | UI 상태 · 그리기 · 상한 있는 계산 | 구문 강조 실행 · 상한 없는 diff 계산 |
| 계산 워커 | Web Worker | 창의 첫 계산 요청부터 | 구문 강조 · diff 토큰 · diff 줄 | 상태 소유 · IPC |
| 하네스 · 도구 프로세스 | 자식 프로세스 | 세션·도구마다 | 모델 호출 · 도구 실행 · git 조회 · 예약 셸 명령 | — |

- 진입점은 셋이다 — `app/src/main/index.ts`(셸) · `app/src/main/app/data-host/entry.ts` ·
  `app/src/main/app/agent-host/entry.ts`. 두 호스트의 시작 순서는 `app/src/main/app/host-process.ts` 가,
  두 호스트 사이의 순서(기동·실패·재기동·종료)는 `app/src/main/app/shell/boot.ts` 가 갖는다.
- 본 화면은 두 호스트가 모두 준비된 뒤에 뜬다. 어느 호스트든 기동이 거듭 실패하면 부팅 오류다. 준비를 알리지 않은 채
  셸과 메시지가 오가지 않는 시간이 마감(`app/shell/host-supervisor.ts` `HOST_READY_TIMEOUT_MS`)을 넘은 호스트는 셸이
  끝내고 기동 실패로 센다. 데이터 호스트의 DB 단계(열기·백업·마이그레이션·복구)는 `boot.step` 시작·끝으로 알려 세지
  않는다 — 끊으면 다시 떠도 백업부터 다시 해 끝나지 못한다.
- 종료는 에이전트 호스트(런타임 정지 → 저장 스트림 비움) 다음에 데이터 호스트(예약 작업 → 스케줄러 →
  DB 닫기) 순서다.

## 연결

| 연결 | 양 끝 | 무엇이 지나가는가 | 정본 |
|---|---|---|---|
| 셸 IPC | 창 ↔ 셸 | 창 조작 · 업데이트 · renderer 로그 · 부팅 대기 · 알림 | `shared/channel-owner.ts` 의 `'shell'` 채널 |
| 창 포트 | 창 ↔ 각 호스트 | 그 호스트가 소유한 채널의 요청·통지. 셸의 JS 와 preload 를 지나지 않는다 — preload 다리가 셸이 넘긴 포트를 페이지 메인 월드의 renderer 전송층에 넘긴다 | `shared/channel-owner.ts` · `shared/host-protocol.ts` · `shared/host-channels.ts` |
| 피어 포트 | 에이전트 호스트 ↔ 데이터 호스트 | 턴 저장 스트림 · 턴 준비 조회 · 설정 사본 · 교차 요청 | `shared/peer-protocol.ts` |
| 셸 서비스 | 각 호스트 → 셸 | Electron 권한 작업 | `shared/host-protocol.ts` |
| 수명 이벤트 | 에이전트 호스트 → 셸 | 턴 시작·끝 · 승인 대기 · 세션 끝 · 하네스 종료 | `app/shell/lifecycle-state.ts` |

- **채널마다 처리하는 프로세스는 하나다.** renderer 전송층(`renderer/src/shared/api/transport/`)이 채널 소유
  표를 보고 preload 다리(셸 IPC)·에이전트 포트·데이터 포트 중 하나를 고른다. 다리는 셸 채널만 연다.
  `window.oo` 의 모양은 전송과 무관하다. preload 는 `electron` 과 zod 없는 shared 상수만 쓴다 — 빌드 산출은
  `scripts/smoke-preload.mjs` 가 본다.
- **턴 이벤트는 두 곳에 함께 간다.** 에이전트 호스트가 이벤트 하나를 데이터 호스트(저장)와 창(표시)에
  보내고, 화면은 저장 응답을 기다리지 않는다. 피어 포트의 순서가 곧 저장 순서다. 저장이 실패하면 그 턴은
  오류로 끝난다. 사용자 메시지 커밋과 백그라운드 기록, 산출물 참조가 붙는 이벤트는 저장 응답 뒤에 공개한다.
- **진행 중 턴의 델타는 빠지지 않는다.** 턴은 시작한 창의 문서와 수명을 같이하고(문서가 닫히면 중단),
  진행 중인 캐시 세션에는 세션 로드 결과를 적용하지 않는다. 턴 이벤트에 순번은 없다 — 창이 여럿이 되거나
  턴이 창보다 오래 살게 되면 이 전제를 먼저 다시 설계해야 한다.
- **호스트가 죽거나 다시 붙으면 renderer 가 안다.** renderer 전송층이 `window.oo.hosts.onLifecycle` 로 알린다. 에이전트
  호스트가 죽으면 진행 중 세션은 오류로 끝나 입력을 다시 받고(그 호스트가 보낼 마감 이벤트는 오지 않는다),
  죽었던 호스트가 다시 붙으면 세션 목록과 활성 세션을 다시 읽는다.
- **세션 본문은 조각으로 간다.** 데이터 호스트가 메시지를 조각으로 나눠 창 포트에 보내고 renderer 전송층이
  한 벌로 조립한다. renderer 는 조립된 결과를 한 번만 스토어에 반영한다. 상한과 조립 규칙은
  `shared/data-host.ts` 가 갖는다.
- **데이터 호스트가 실행이 필요한 일**(예약 셸 명령 · 네이티브 이력 읽기 · 하네스 설치·모델 목록 ·
  확장 배포)을 부탁할 때 에이전트 호스트가 없으면 셸에 기동을 요청하고 기다린다. 활동 조회·바쁨 판정·
  런타임 폐기는 기동을 부르지 않는다 — 없으면 쉬는 상태다.
- **에이전트 호스트는 데이터 호스트의 것을 사본으로 본다.** 설정은 연결 때 전체를, 이후 패치를 받는다.
  플러그인·산출물 도구와 관리형 MCP 는 서술자 사본으로 받아 호출을 데이터 호스트로 대신 보낸다. 셸은 준비
  직후 창 포트를 넘기고 피어 포트는 그 뒤라, 에이전트 호스트는 첫 설정 사본을 받기 전에 온 창 요청을 도착
  순서대로 기다리게 한다(`app/host-port-server.ts` `hold`). 동기로 판정해야 하는 세션 메타·백그라운드 기록은
  lease 변화·턴 시작·판정 직전에 데이터 호스트에서 다시 받아 둔다(`app/agent-host/session-meta.ts`·
  `background-records.ts`).

## 경로 표 — 누구에게 어떤 경로로 부탁하는가

| 하려는 일 | 요청하는 곳 | 경로 | 직접 하면 걸리는 규칙 |
|---|---|---|---|
| renderer 가 데이터를 읽거나 바꾼다 | 채널을 소유한 프로세스 | `renderer/src/shared/api/*` → `window.oo`(전송층) → 채널 소유 표 → 호스트 포트 또는 preload 다리(셸 IPC) | (h) |
| 호스트가 화면을 갱신시킨다 | renderer | `infra/ipc/send.ts` 의 통지 함수 → 창 포트 → `shared/api` 구독 → 스토어 | (g) |
| renderer 가 무거운 계산을 한다 | 계산 워커 | `renderer/src/shared/compute/client.ts` | (b)(i) |
| renderer 가 세션 본문을 읽는다 | 데이터 호스트 | `sessionApi.load`·`refresh` → 전송층 조립 → `app/data-host/session-load.ts` | (c) |
| 호스트가 창·OS·비밀 봉인을 쓴다 | 셸 | 셸 서비스 클라이언트 | (f) |
| 셸이 턴·세션 상태를 안다 | 에이전트 호스트 | 수명 이벤트 → `LifecycleState` | (e) |
| 실행 쪽이 DB·설정·비밀을 읽거나 쓴다 | 데이터 호스트 | 데이터 링크(`data.query`·`data.write`) · 설정 사본 | (e)(k)(l) |
| 상태 쪽이 하네스·프로세스가 필요한 일을 한다 | 에이전트 호스트 | 에이전트 링크(`agent.call`) | (e) |
| 프로세스를 띄운다 | 등록된 기동 모듈 | `infra/git/runner` · `infra/shell/shell-runner` · 하네스 어댑터 · 셸의 호스트 감독 | (j) |
| 요청 핸들러를 등록한다 | `infra/ipc/handle.ts` | `handle` · `handlePlain` · `on` | (d) |
| 파일을 읽는다 | 비동기 API | `fs/promises` | (a) |

규칙 (e) 는 프로세스마다 다르다.

| 그래프 | 진입점에서 값 import 로 닿으면 안 되는 것 |
|---|---|
| 셸 | `features/` · `adapters/` · `infra/db/` · SQLite 패키지 · `worker_threads` |
| 에이전트 호스트 | 앱 DB(`infra/db/` — 범용 SQLite 열기 한 파일 제외) · 설정·비밀 파일 모듈 · `electron-store` · 데이터 호스트 조립 폴더(`app/data-host/`) |
| 데이터 호스트 | 하네스 어댑터·서버 구현 · 하네스 SDK · `child_process` · 에이전트 호스트 조립 폴더(`app/agent-host/`). `adapters/common/` 은 허용하고, 하네스별 폴더에는 등록한 구성 읽기 입구로만 들어간다 |

- 에이전트 호스트의 범용 SQLite 열기는 하네스가 자기 저장소를 SQLite 로 두는 경우(네이티브 이력 읽기)를
  위한 것이다. 앱 DB 는 열지 않는다.
- 두 호스트가 나누는 것은 계약(`shared/peer-protocol.ts`)과 공용 호스트 인프라(`app/host-process.ts` ·
  `app/host-runtime.ts` · `app/host-port-server.ts` · `app/host-shell-client.ts`)다. 서로의 조립 폴더는
  타입으로만 import 한다.
- 데이터 호스트의 구성 읽기 입구는 파일만 읽는다(설정 트리 · 스킬·플러그인 목록). 그 안쪽에서 SDK 나
  프로세스 기동에 닿으면 같은 규칙이 실패한다.

## 멈춤 계측

셸과 두 호스트는 이벤트 루프가 멈춘 구간을 `perf.stall` 로 남긴다(`thread` 가 프로세스 이름이다). 요청
처리(셸 IPC · 창 포트 요청 · 피어 수신)의 동기 구간도 채널 또는 메시지 종류 이름과 함께 남는다. renderer
는 긴 작업을 같은 이벤트로 보고한다. 기준값의 정본은 `app/src/shared/perf-budget.ts` 다.

이 절은 그 파일의 기준 이름과 뜻만 적고 값은 적지 않는다. 한 작업이 `UI_TASK_BUDGET_MS` 이상 스레드를 잡으면
멈춤으로, `STALL_SEVERE_MS` 이상이면 심각으로 기록한다. 관측 창 `STALL_WINDOW_MS` 하나에는 그 창의 최댓값
기록 하나만 남는다.

UI 스레드(renderer 메인 · 셸)에서 한 작업을 여러 태스크에 나눠 도는 시간 조각 작업은 `UI_YIELD_INTERVAL_MS`
마다 양보한다(0324 D-057). 한 번에 끝나는 작업(이벤트 처리 · 프레임마다 모은 델타 비우기 · 스토어 반영)은 위의
멈춤 기준이 맡는다. 지금 해당하는 것은 React 지연 렌더(`useDeferredValue` · `startTransition`)뿐이고 React
스케줄러가 같은 간격으로 양보한다 — 직접 나눠 도는 코드를 새로 만들면 이 기준을 쓴다. 강제 수단은 `강제 없음`
이다(가드가 보지 않는다).

로그는 프로세스마다 자기 파일에 쓴다. 오류 보고와 부팅 보고는 데이터 호스트가 모아 창에 준다 — 에이전트 호스트는 자기 보고를 피어 포트로 넘기고(`report.error`·`report.boot`), 데이터 호스트는 오류 보고를 자기 허브로 내고 부팅 단계를 자기 단계와 합친다. 피어가 없는 동안의 오류 보고는 상한까지 보관했다가 연결되면 보낸다.

## 새 코드를 어디에 두는가

1. 하네스·SDK·git·셸 프로세스에 닿는가 → 에이전트 호스트. DB·설정이 필요하면 데이터 링크로 묻는다.
2. DB·설정·비밀·인증 파일에 닿는가 → 데이터 호스트. 실행이 필요하면 에이전트 링크로 부탁한다.
3. Electron 의 창·OS API 인가 → 셸 서비스에 이름을 더하고 호스트는 그것을 부른다.
4. 새 채널이면 `shared/channel-owner.ts` 에 소유 프로세스를 적는다 — 적지 않으면 타입 검사가 실패한다.
5. 창에서 오래 걸리는 계산이면 계산 워커로 보낸다.
