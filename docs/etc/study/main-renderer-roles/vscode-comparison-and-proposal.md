## 1. VS Code 사례에서 가져올 원칙

참조 문서의 결론은 "main 이 큰 계산을 잘 버티게 만드는 것이 아니라, 계산·I/O 대기·UI 반영을 각 실행 주체에 배치하고 각자의 작업량을 제한한다"다. Orcinus orca 에 옮길 수 있는 형태로 줄이면 다섯이다.

| # | 원칙 | 참조 문서의 근거 |
|---|---|---|
| P1 | **main 은 창·OS·서비스 연결·프로세스 수명만 맡는다.** DOM 을 갱신하지 않고 "다시 그려라"를 보내지도 않는다 | 사례 B — 최대화는 main 이 창을 바꾸고 **상태 이벤트**만 보낸다 |
| P2 | **UI 상태와 그리기 예약은 renderer 가 소유한다.** main 을 거칠 필요가 없는 조작은 renderer 안에서 끝난다 | 사례 A — 사이드바 토글 |
| P3 | **CPU 계산은 그 결과를 쓰는 쪽 옆의 워커에 둔다.** 결과는 main 을 거치지 않고 소비자에게 바로 돌아온다 | 사례 C — diff 는 renderer ↔ Web Worker |
| P4 | **장수명 서비스는 별도 프로세스가 소유하고, main 은 띄우고 포트만 넘긴다.** 정상 데이터는 main JS 를 지나지 않는다 | 확장 호스트·파일 감시 utility process + MessagePort |
| P5 | **받는 쪽도 작업량을 줄인다.** 묶기·중복 예약 억제·부분 갱신. 워커로 옮기는 것만으로는 프레임 지연이 사라지지 않는다 | diff 200ms 묶기 · 편집기 rAF 예약 · 검색 뷰 throttle |

함께 가져올 주의점.

- `async`/`await` 는 실행 위치를 바꾸지 않는다. 기다리는 동안만 이벤트 루프를 돌려준다.
- 보호해야 할 이벤트 루프가 둘이다 — main 과 renderer.
- IPC 는 공짜가 아니다. 크거나 잦으면 보내는 쪽과 받는 쪽이 모두 병목이 된다.
- 워커에는 취소·종료·실패·결과 버전 처리가 따라온다.

## 2. Orcinus orca 의 현재 배치

### 2.1 실행 주체

| 실행 주체 | 지금 하는 일 | 근거 |
|---|---|---|
| main 프로세스 (JS 한 스레드) | 창·IPC·턴 구동·이벤트 정규화·DB 읽기/쓰기·설정/플러그인 파일 읽기·사용량 집계·편집 미리보기 diff | `app/src/main/**` |
| renderer (창마다 한 스레드) | 상태 스토어·reducer·Markdown 변환·구문 강조·diff 줄 조립·가상 스크롤 | `app/src/renderer/**` |
| 자식 프로세스 | 하네스 실행(Claude CLI · OpenCode 서버) · git | `adapters/claude` · `adapters/opencode` · `infra/git` |
| Web Worker · `worker_threads` · `utilityProcess` | **없다** | `rg 'new Worker\(\|new SharedWorker\(\|utilityProcess\|worker_threads' app/src` (테스트 제외) → 주석 1건 |

### 2.2 이미 잘 되어 있는 것

"전부 주니어 수준"이라는 전제는 코드와 맞지 않는다. 가장 뜨거운 경로인 스트리밍 표시는 P5 를 이미 지킨다.

| 경로 | 구현 | 근거 |
|---|---|---|
| 스트리밍 델타 수신 | reducer 를 거치지 않고 코얼레서가 모아 `requestAnimationFrame` 에 한 번 반영한다 | `renderer/src/features/chat/store/chatStore.ts` — "델타는 여기 오지 않는다 — 코얼레서가 전량", `schedule: (cb) => requestAnimationFrame(cb)` |
| 스트리밍 Markdown | 확정된 앞부분과 자라는 꼬리를 갈라 꼬리만 다시 변환한다 | `shared/ui/markdown/streamingContext.ts` |
| 스트리밍 중 구문 강조 | 꼬리의 코드 블록은 강조를 건너뛴다 — 프레임마다 전체를 다시 강조하는 O(n²) 를 피한다 | 같은 파일 주석(0108) |
| 긴 대화 | 교환·행 단위 가상 스크롤 | `features/chat/hooks/useTranscriptVirtualizer.ts` |
| 델타 저장 | 델타는 DB 에 쓰지 않는다 | `main/features/history/writer.ts` — "message.delta/message.reasoning.delta/turn.retrying 은 transient(미저장)" |
| 가장 무거운 일 | 에이전트 실행과 git 은 프로세스 밖이다 | §2.1 |
| 편집 미리보기 | 파일 크기를 먼저 재고 상한을 넘으면 읽지 않는다 | `adapters/claude/edit-preview.ts` |
| DB | WAL 모드 — 읽기와 쓰기가 서로를 막지 않는다 | `infra/db/file-database.ts` |

### 2.3 원칙에 어긋나는 것

| # | 관측 | 어긋나는 원칙 | 근거 | 확신 |
|---|---|---|---|---|
| G1 | **계측이 하나도 없다.** main 이벤트 루프 지연, renderer 긴 작업, IPC 건수·크기를 재는 코드가 없다 | 전부 — 무엇이 느린지 모른 채 고치게 된다 | `rg 'monitorEventLoopDelay\|performance\.mark\|PerformanceObserver\|eventLoopUtilization' app/src` (테스트 제외) → 0건 | 확인 |
| G2 | **계산을 맡길 워커가 없다.** main 과 renderer 가 각자 자기 스레드에서 전부 한다 | P3 · P4 | §2.1 | 확인 |
| G3 | **DB 가 main 스레드에서 동기로 돈다.** `better-sqlite3` 는 동기 API 다 | P1 | `rg '\.prepare\(' app/src/main` (테스트 제외) → 160건 | 확인. 실제 지연은 미측정 |

수준에 대한 판단: 뜨거운 경로 하나는 공들여 만들었고, **그 밖의 일을 어디에 둘지에 대한 규칙과 측정 수단이 없다.** 고칠 것은 개별 코드의 솜씨보다 이 두 가지다.

## 3. VS Code 사례와 Orcinus orca 의 대응

| VS Code 사례 | Orcinus orca 에서 같은 모양 | 지금 상태 |
|---|---|---|
| A — 사이드바 토글(renderer 안에서 끝) | 우측 타일 열기·닫기, 패널 크기 조절 | 이미 renderer 안에서 끝난다 |
| B — 최대화(main 이 바꾸고 상태 이벤트로 알림) | 권한 모드 변경 — main 이 적용한 모드를 이벤트로 돌려준다 | 같은 모양이다(`state.md` "라이브 권한 응답") |
| C — diff 계산(renderer ↔ Web Worker) | 구문 강조 · diff 줄 강조 | **renderer 메인 스레드에서 한다**(G7) |

| 받는 쪽 묶기 | 델타 코얼레서 | 있다 |

## 4. 역할 재정의 — 제안

### 4.1 한 줄 규칙

| 실행 주체 | 맡는다 | 맡지 않는다 |
|---|---|---|
| **main** | 창·OS·권한 판정·IPC 라우팅·자식/워커 프로세스의 수명·짧은 검증·**쓰기 순서가 중요한 저장** | 입력 크기에 비례하는 계산 · 동기 파일 읽기 · 화면 갱신 지시 |
| **renderer** | UI 상태·그리기 예약·받은 결과의 묶기와 부분 갱신 | 입력 크기에 비례하는 계산(강조·대형 변환) |
| **renderer 워커**(신규) | renderer 가 쓸 순수 계산 — DOM 없이 되는 것 | 상태 소유 · IPC |
| **데이터 프로세스**(신규, 뒤 단계) | 읽기 전용 대량 조회와 변환 — 세션 로드·사용량 집계·native 이력 읽기 | 쓰기 · 권한 판정 |
| **하네스·git 프로세스**(기존) | 에이전트 실행 · git | — |

### 4.2 main 핸들러 규칙

main 에서 도는 모든 것 — IPC 핸들러, 턴 이벤트 처리, 훅 — 에 같은 규칙을 건다.

1. **받아서 넘긴다.** 핸들러는 검증하고, 일을 맡기고, 돌아온다. 입력 크기에 비례하는 반복을 직접 돌지 않는다.
2. **파일은 비동기로 읽는다.** `*Sync` 는 부팅 초기화와 마이그레이션에만 허용한다.
3. **상태는 이벤트로 알린다.** 요청의 반환값으로 화면을 바꾸게 하지 않는다 — 다른 계기로 같은 상태가 바뀌어도 한 경로로 반영된다(사례 B).
4. **큰 것은 나눠 보낸다.** 한 번의 응답에 세션 전체를 담지 않는다.
5. **잦은 것은 묶어 보낸다.** 같은 종류의 통지는 이벤트 루프 한 바퀴에 한 번.

### 4.3 renderer 규칙

1. **받은 것을 프레임에 묶는다** — 델타 코얼레서가 하는 방식을 다른 고빈도 통지에도 쓴다.
2. **계산은 워커에, 반영은 메인 스레드에.** 워커 결과는 "아직 그 내용이 화면에 있는가"를 확인하고 반영한다.
3. **워커가 실패하면 강조 없이 그린다.** 동기 대체 경로를 두지 않는다 — VS Code 의 diff 는 워커 실패 시 메인 스레드로 돌아가는데, 그 경로가 곧 멈춤의 원인이 된다.

## 5. 워커 운영 — 제안

### 5.1 무엇을 어디에

| 일 | 지금 | 제안 | 종류 | 이유 |
|---|---|---|---|---|
| 구문 강조(코드 블록 · diff) | renderer 메인 스레드 | **renderer Web Worker** | 스레드 | 순수 계산이고 결과를 renderer 가 쓴다. main 을 거칠 이유가 없다(P3) |
| 세션 로드 | main 동기 DB + 단일 응답 | **데이터 프로세스**가 읽기 전용 연결로 조회하고 조각으로 보낸다 | 프로세스 | WAL 이라 읽기 연결을 따로 열 수 있다. 쓰기 경로를 건드리지 않는다 |
| 사용량 집계 | main, telemetry 마다 | 먼저 **묶기**(한 턴에 한 번). 그래도 느리면 데이터 프로세스 | — → 프로세스 | 워커보다 횟수를 줄이는 쪽이 싸다(P5) |
| 설정·플러그인 파일 읽기 | main 동기 | **비동기 읽기로 바꾼다.** 워커 불필요 | — | I/O 대기는 워커가 아니라 비동기로 푼다 |
| DB 쓰기(이력 저장) | main 동기 | **그대로 둔다** | — | 건당 작고 순서가 중요하다. 옮기면 모든 호출부가 비동기가 된다 |
| 턴 이벤트 정규화 | main | **그대로 둔다** | — | 이벤트당 가볍다. 훅 sink 도 "적재만" 규칙을 따른다 |
| 편집 미리보기 diff | main, 크기 상한 있음 | 그대로 두고 **계측만** | — | 상한이 이미 있다 |

### 5.2 워커를 몇 개, 어떻게

| 항목 | renderer Web Worker | 데이터 프로세스 |
|---|---|---|
| 개수 | 창마다 1 | 앱에 1 |
| 수명 | 처음 쓸 때 만들고 창과 함께 끝난다 | 처음 쓸 때 띄우고, 한동안 안 쓰면 내린다 |
| 통신 | `postMessage` — 요청 번호로 응답을 짝짓는다 | 띄우는 것은 main, 데이터는 renderer 와 `MessagePort` 로 직접(P4) |
| 취소 | 요청 번호를 버린다 — 늦게 온 결과는 반영하지 않는다 | 같다 + 세션 전환 시 진행 중 조회를 버린다 |
| 실패 | 강조 없는 표시로 남는다 | main 의 기존 경로로 한 번 대체하고 기록한다 |
| 종료 | 창 닫힘 | 앱 종료 시 main 이 내린다. 비정상 종료는 다음 요청 때 다시 띄운다 |
| 빌드 | electron-vite 의 워커 번들 | `better-sqlite3` 는 Electron ABI 그대로 쓴다. 패키징에 진입 파일이 하나 는다 |

만들지 않는 것: 범용 작업 큐, 워커 풀, main 의 `worker_threads`. 지금 확인된 계산 중 그것을 요구하는 것이 없다.

### 5.3 순서 — Orcinus orca 수준에 맞춘 단계

각 단계는 앞 단계의 측정 결과가 다음 단계의 근거가 된다. 뒤 단계는 측정이 필요를 보이지 않으면 하지 않는다.

| 단계 | 내용 | 바뀌는 동작 | 위험 | 다음 단계로 가는 조건 |
|---|---|---|---|---|
| 0 | **계측을 넣는다** — main 이벤트 루프 지연, renderer 긴 작업, IPC 채널별 건수·크기, 세션 로드 구간별 시간 | 없음 | 낮음 | 수치가 나온다 |
| 1 | **규칙을 문서에 넣는다**(§4.2 · §4.3) + 값싼 위반 정리 — 동기 파일 읽기를 비동기로, 사용량 집계 묶기 | 없음 | 낮음 | — |
| 2 | **구문 강조를 renderer 워커로** | 긴 코드 블록·큰 diff 를 열 때 화면이 멈추지 않는다 | 중간 — 강조가 늦게 입혀지는 깜빡임 | 0 의 긴 작업 기록에 강조가 보인다 |
| 3 | **세션 로드를 조각으로** — 먼저 main 안에서 나눠 보내기 | 큰 세션이 앞부분부터 보인다 | 중간 — 순서·미완료 표시 회귀 | 0 의 세션 로드 시간이 크다 |
| 4 | **데이터 프로세스** — 3 의 조회를 프로세스로 옮긴다 | 큰 세션을 여는 동안 다른 세션의 스트리밍이 밀리지 않는다 | 높음 — 새 프로세스의 수명·패키징 | 3 뒤에도 main 지연이 남는다 |
| 5 | **델타 송신 묶기** | 없음(표시는 이미 프레임에 묶인다) | 낮음 | 0 의 IPC 건수가 문제를 보인다 |

단계 0·1 은 무엇을 고르든 먼저 한다. 2 와 3 은 서로 독립이다.

## 6. 훅·패널 작업(0323)과의 관계

## 7. 결정이 필요한 것

## 8. 이 조사가 확인하지 않은 것

- 실제 지연·프레임 시간·IPC 비용 — 전부 미측정이다. §2.3 의 G3~G8 은 "원칙에 어긋나는 배치"이지 "느리다는 증거"가 아니다.
- 동기 파일 읽기 각 자리의 호출 빈도(부팅 한 번인지 요청마다인지).
- OpenCode 스트리밍 경로의 renderer 쪽 묶기가 Claude 와 같은지.
- electron-vite 워커 번들과 `utilityProcess` 가 현재 빌드·패키징 설정에서 추가 작업 없이 되는지.
- 참조 문서의 VS Code 소스 — 문서의 서술을 그대로 받았고 소스를 다시 대조하지 않았다.

## 9. 자기 검토 (2026-11-16, 사용자 질의 뒤)

질문은 둘이었다 — 이 제안이 참조 문서의 개념을 충실히 반영했는가, 버벅임이 없음을 구조적으로 자신할 수 있는가.

### 9.1 참조 문서 대비 빠지거나 약한 곳

| # | 참조 문서의 개념 | 이 제안의 처리 | 판정 |
|---|---|---|---|
| R1 | 장수명 세션·스트림은 **별도 프로세스가 소유**하고, main 은 띄우고 포트만 넘긴다. 정상 데이터는 main JS 를 지나지 않는다 | §5.1 에서 "턴 이벤트 정규화 → 그대로 main"으로 두었다. 근거는 "이벤트당 가볍다"였고 **측정하지 않았다** | **가장 큰 누락.** 모든 세션의 SDK 스트림 해석·정규화·저장·전달이 main JS 한 스레드를 지난다. 참조 문서의 확장 호스트에 해당하는 "세션 호스트 프로세스"를 선택지로 올리지 않았다 |
| R2 | 받는 쪽의 **동기 처리량**도 프레임을 늦춘다(워커 응답 → 모델 → 뷰 이벤트는 같은 스레드의 동기 호출) | renderer 는 구문 강조만 짚었다 | 약함. reducer 복사, 알림마다 메시지 전체를 도는 selector, 확정된 Markdown 의 동기 변환을 다루지 않았다 |
| R3 | 워커는 **모델을 복제하고 증분으로 동기화**한다. 최초 전송과 메시지 처리 비용이 남는다 | 강조 워커를 "요청마다 `postMessage`"로만 적었다 | 약함. 큰 코드·diff 를 매번 통째로 보내는 비용을 다루지 않았다 |
| R4 | **취소 확인은 계산 중단이 아니다** | "요청 번호를 버린다"고 적었다 | 부분 반영. 창당 워커가 하나라 큰 요청 하나가 뒤 요청을 막는 것을 다루지 않았다 |
| R5 | 서비스 호출의 실행 위치는 이름이 아니라 **주입된 구현과 채널 등록**을 따라가야 안다 | 규칙을 문서에 넣자고만 했다 | 약함. 규칙을 **기계로 강제**하는 수단이 없다 |
| R6 | 실제 성능은 프로파일과 도착·반영·프레임 시각을 **함께 측정**해야 한다 | 단계 0 | 반영 |
| R7 | 상태는 응답이 아니라 **상태 이벤트**로 반영한다 | §4.2 규칙 3 | 반영 |
| R8 | 워커 실패 시 **동기 대체 경로**가 멈춤의 원인이 된다 | §4.3 규칙 3 | 반영 |

### 9.2 버벅임이 없음을 구조적으로 자신할 수 있는가

**자신할 수 없다.**

| 이유 | 내용 |
|---|---|
| 측정이 없다 | 이 문서의 어떤 주장도 지연 시간으로 뒷받침되지 않는다 |
| main 이 여전히 한 스레드다 | 제안대로 해도 모든 세션의 스트림과 동기 DB 쓰기가 main 을 지난다(R1). 동시에 여러 세션이 흐르면 서로를 늦출 수 있고, 창 조작과 입력 전달도 같은 스레드다 |
| renderer 도 한 스레드다 | React 갱신·Markdown 변환·레이아웃은 워커로 옮길 수 없다. 묶기로 횟수를 줄일 뿐이다(R2) |
| 규칙은 강제가 아니다 | 문서의 규칙은 다음 사람이 어기면 그만이다(R5) |
| 앱 밖의 요인 | 하네스 프로세스와의 CPU·메모리 경합은 프로세스 분리로 없어지지 않는다 |

구조로 말할 수 있는 것은 **"한 번에 하는 일의 크기에 상한이 있다"**까지다. 그것도 상한을 기계가 검사할 때만 성립한다.

### 9.3 자신할 수 있는 수준으로 올리려면

| 보강 | 내용 | 닫는 항목 |
|---|---|---|
| 세션 호스트 프로세스를 선택지로 올린다 | SDK 호출·어댑터·정규화를 `utilityProcess` 가 소유하고 renderer 와 `MessagePort` 로 직접 통신. main 에는 창·권한·수명만 남는다. **가장 큰 구조 변경**이라 계측(단계 0)이 "main 이 실제로 밀린다"를 보일 때만 한다 | R1 |
| 규칙을 lint 로 강제한다 | `*Sync` 파일 API 와 DB 모듈 import 를 허용 디렉토리 밖에서 금지 — 이미 쓰는 `eslint-plugin-boundaries` 위에 얹는다 | R5 |
| 부하 시험을 게이트로 둔다 | 세션 N 개가 동시에 스트리밍하는 합성 부하에서 main 이벤트 루프 지연과 renderer 긴 작업의 상한을 단언한다. "자신한다"를 말이 아니라 실패하는 시험으로 바꾼다 | 측정 없음 |
| renderer 동기 처리량을 조사 범위에 넣는다 | reducer · selector · Markdown 변환의 입력 크기별 비용을 단계 0 의 계측 대상에 추가한다 | R2 |
| 강조 워커의 전송·대기를 설계한다 | 같은 내용의 재전송을 피하는 키, 보이는 블록 우선, 오래 걸리는 요청의 분할 | R3 · R4 |

§5.3 의 순서는 유지하되 단계 0 의 결과에 따라 "세션 호스트 프로세스"가 단계 4 의 데이터 프로세스보다 앞설 수 있다.
