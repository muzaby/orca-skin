# 7. 큰 그림: 비전과 그 필요조건의 구현

운영체제론은 "OS 가 되기 위해 *필연적으로* 제공해야 하는 것"(프로세스·메모리·I/O·보호)을
규정하고 각 OS 가 그것을 어떻게 구현했는지 본다. 같은 논리를 opencode 에 적용한다. 먼저 비전을
규정하고, 그 비전이 *요구하는* 필요조건을 도출한 뒤, 각각이 어떤 골격으로 구현됐는지를 1–6장의
코드에 근거해 본다.

## 7.1 이 프로젝트의 비전 / 철학 / 방향

코드가 실제로 최적화하는 대상에서 도출한 opencode 의 비전은:

> **"여러 모델·여러 클라이언트에서 동작하는, 오래 도는 자율 코딩 에이전트를, 프로토콜 수준까지
> 직접 통제하면서, 안전하게 운영한다."**

이 한 문장을 코드가 어떻게 뒷받침하는가:

- **클라이언트/서버 분리** (CLI·TUI·GitHub 가 전부 서버의 클라이언트, `cli/cmd/run.ts` 도
  `sdk.session.prompt`) → "에이전트는 하나의 서비스, UI 는 갈아끼운다"는 방향.
- **자체 LLM 프로토콜 패키지**(`@opencode-ai/llm`, 11종 프로바이더) → "모델 벤더에 종속되지
  않고 wire 레벨까지 통제"하려는 의지. SDK 는 폴백일 뿐.
- **모델별 프롬프트·툴 분기**(`session/prompt/*.txt`, `registry.ts:273`) → 단일 모델 가정이
  아니라 **이기종 모델 다수**가 전제.
- **권한 게이트·둠루프 감지·압축**이 1급 모듈 → "자율적으로 오래 돌되 폭주/오염되지 않게"가
  핵심 관심사. 즉 *자율성과 안전·지속성의 동시 추구*.

이 비전은 "최소·투명한 에이전트"(예: 단일 파일 데모)와는 정반대 지점에 있다. opencode 는
**프로덕션 멀티모델 플랫폼**을 지향하므로, 아래 필요조건들이 대부분 "필요함"으로 나온다.

## 7.2 비전이 요구하는 필요조건과 그 구현

| 후보 조건 (OS 주제) | 이 비전에 필요한가? | 어떤 골격·구조로 구현했나 (코드 근거) |
|---|---|---|
| **부팅 / 초기화** | **필요** — 멀티서비스 서버이므로 다수 서비스의 순서 있는 기동이 필수 | Effect **Layer/LayerNode 의존 그래프**. 각 모듈이 `LayerNode.make(layer, [deps])` 로 의존을 선언(`run-state.ts:154`, `registry.ts:418`)하고 위상 정렬로 단일 런타임 레이어 구성. 서버는 인스턴스 컨텍스트(`InstanceState`)와 함께 기동. provide 누락은 컴파일 타임에 차단. |
| **프로세스 & 수명주기** | **필요** — "task = 하나의 세션 실행"이 프로세스에 해당 | **세션이 곧 프로세스**. `loop→ensureRunning→runLoop`(`prompt.ts:1386`,`1134`)가 세션 수명주기를 정의. 시작=user 메시지, 진행=step 반복, 종료=종료조건(3장). 서브에이전트 = **자식 프로세스**(`task` 툴이 자식 세션 스폰, `handleSubtask`). |
| **스케줄링** | **부분적 필요** — 단일 세션 내 "다음 행동"은 모델이 정함. 단 동시 실행 통제는 필요 | 다음 행동 선택은 **LLM 이 스케줄러**(툴콜로 다음 step 결정). 시스템 측 스케줄링은 ① 세션당 **단일 실행**(`ensureRunning`, busy 면 `BusyError`, `run-state.ts:74`), ② 네이티브 툴 settlement 의 **동시 실행**(`FiberSet`, `native-runtime.ts:106-133`), ③ 백그라운드 서브에이전트(`task background=true`). 선점형 OS 스케줄러는 **해당 없음**(필요 없음 — 협력적). |
| **메모리 관리** | **필요(핵심)** — 오래 도는 에이전트는 유한 컨텍스트가 곧 생사 | **3단 컴팩션**: 오버플로 감지(`isOverflow`) → 요약 압축(head 요약 + tail 토큰예산 보존 `select/splitTurn`, 기본 `tail_turns=2`) → 프루닝(`PRUNE_PROTECT=40,000` 보호 후 오래된 툴 출력 제거). 루프가 오버플로를 만나면 자동 압축 큐잉(`prompt.ts:1214-1221`). = "유한 컨텍스트를 비전(장기 자율)에 맞게 회수"하는 페이징 유사 전략. |
| **I/O & 시스템콜** | **필요** — 외부 세계와의 경계가 곧 에이전트의 능력 | **툴 = 시스템콜 인터페이스**. 내장 13종(read/write/edit/shell/grep/glob/fetch/...) + 커스텀/플러그인/MCP(`registry.ts:219`). 정의는 공통 `Tool.Def`, 실행은 런타임별 어댑터. LLM 호출 자체도 I/O: `LLMEvent` 스트림으로 정규화된 단일 경계(`llm.ts`). |
| **동시성 & 동기화** | **필요** — 스트리밍·취소·서브에이전트·권한 대기가 공존 | Effect 의 `Fiber/FiberSet`(네이티브 툴 동시 settle), `Deferred`(권한 대기 동기화, `permission/index.ts:109`), `Latch`(셸 준비 신호, `prompt.ts:1395`), `Queue`(네이티브 결과 채널). 인터럽트 안전 정리는 `onInterrupt`+`ensuring`(`prompt.ts:1272-1376`). |
| **보호 & 권한** | **필요(핵심)** — 자율 + 파일/셸 접근은 본질적으로 위험 | **권한 게이트**(`permission/index.ts`): allow/ask/deny 룰셋 평가, ask 면 `Deferred` 로 툴 실행 블록 후 사용자 승인 대기. 에이전트별 권한셋(`agent.permission`), 서브에이전트 권한 파생(`subagent-permissions.ts`), `plan` 모드는 편집 툴 차단. **둠루프 감지**(`processor.ts:522`)도 보호의 일종(자원 폭주 차단). = blast radius 봉쇄. |
| **파일시스템 & 영속성** | **필요** — 세션 재개·복구·공유가 비전(오래 도는 서비스)의 일부 | **이중 영속화**: JSON 파일 스토리지(`storage/storage.ts`, 마이그레이션 포함) + SQLite `Database`. 메시지/파트/세션이 전부 영속화되고 v2 이벤트로 미러링. 멀티에이전트 토폴로지조차 **메시지 파트에 영속**되어 재구성 가능(5.8). `fork`/`revert`/`archive` 지원(`session.ts`). |
| **에러 처리 & 복구** | **필요** — 프로바이더는 불안정, 턴은 중단됨 | **재시도 정책**(`SessionRetry.policy`, `processor.ts:994-1025`)이 스트림을 감싸 프로바이더 오류를 재시도하며 사용자에게 attempt 상태 통지. **인터럽트 복구**: 중단된 assistant 메시지를 `finalizeInterruptedAssistant` 로 일관 마감(`prompt.ts:1256`). content-filter/구조화출력 실패를 타입드 에러로 표면화(`prompt.ts:1344-1358`). 오버플로 실패는 압축으로 자동 복구. |

## 7.3 종합: 왜 이렇게 만들어졌는가

표로 환원되지 않는 통찰은, **opencode 의 구조 거의 전부가 "오래 도는 멀티모델 자율 에이전트를
안전하게"라는 비전이 부과한 필요조건들에 대한 의도적 답변**이라는 점이다.

- 비전이 *멀티모델·프로토콜 통제*를 요구하므로 → 자체 `@opencode-ai/llm` 패키지와 `LLMEvent`
  정규화 시임, 모델별 프롬프트/툴 분기가 나온다. (단일 모델 데모라면 전부 불필요한 복잡도)
- 비전이 *장기 자율*을 요구하므로 → 3단 컴팩션, 영속화 이중화, fork/revert, 인터럽트 복구가
  1급 시민이 된다. (단발 질의응답이라면 메모리 관리는 truncate 한 줄이면 끝)
- 비전이 *안전*을 요구하므로 → 권한 게이트(Deferred 블록), 둠루프 감지, 서브에이전트 권한
  파생, plan 모드가 핵심 모듈로 승격된다.
- 비전이 *서비스화*(여러 클라이언트)를 요구하므로 → 클라이언트/서버 분리, 이벤트 버스,
  Effect Layer DI 가 기반이 된다.

**의식적으로 만들지 않은 것**도 비전과 정합적이다:

- **하드 step 상한으로 죽이는 안전장치는 기본 없음**(`agent.steps ?? Infinity`,
  `prompt.ts:1231`). 대신 maxSteps 도달 시 *프롬프트로 착지*시킨다. → "자율성을 카운터로
  꺾지 않는다"는 철학. 통제는 권한·둠루프 같은 *의미 기반* 게이트로 한다.
- **선점형 시스템 스케줄러 없음**. 다음 행동은 모델이 정하는 협력적 모델 — "에이전트의 판단을
  시스템이 대신하지 않는다".
- **프레임워크(LangChain 등) 미사용**. 루프·툴·메모리를 직접 들고 있어야 위 필요조건들을
  원하는 형태로 통제할 수 있기 때문. AI SDK 도 *프로토콜 폴백*으로만 격하해, 통제권을 코어에
  남겨둔다.

요컨대 opencode 는 "최소 투명 에이전트"의 반대편에 선, **필요조건을 정면으로 다 떠안은 프로덕션
플랫폼**이다. 그 복잡도(Effect, 이중 런타임, 3단 컴팩션, 권한 시스템)는 군더더기가 아니라
비전이 강제한 *필수 비용*이며, 각 부분이 어떤 필요조건의 답인지가 코드에서 또렷이 추적된다.
